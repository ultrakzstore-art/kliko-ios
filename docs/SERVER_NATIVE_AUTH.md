# Нативный вход через Apple и Google и подключение соцсетей — что нужно от сервера

Документ для разработчика сайта kliko.kz. Приложение iOS (bundle id `kz.kliko.app`) уже умеет эти сценарии
нативно, но **пока сервер их не поддерживает, приложение само откатывается на прежние страницы сайта** — ничего не
ломается. Как только эндпоинты ниже появятся на сервере, приложение начнёт ими пользоваться без обновления.
Исключение — Google (раздел 3): страницы сайта для него нет, поэтому до готовности сервера кнопки Google в
приложении просто нет.

Сессия приложения — та же, что у сайта: кука сессии (`kliko_cab`) в хранилище WebKit приложения. Ниже «вошедший» —
это запрос с этой кукой.

---

## 1. Вход через Apple: `POST /apple_auth.php?action=native`

### Как работает в приложении

1. Приложение генерирует случайный `nonce` (32 байта, hex, 64 символа), показывает системный лист Apple с
   `requestedScopes = [fullName, email]` и передаёт Apple **`hex(sha256(nonce))`** (строчные hex-символы).
2. Apple возвращает `identityToken` (JWT), `authorizationCode`, `user` (sub), имя и почту (имя и почта — **только при
   первом входе** этим Apple ID в приложение; дальше пустые).
3. Приложение шлёт их на сервер (URLSession, не из страницы).

### Запрос

```
POST https://kliko.kz/apple_auth.php?action=native
Content-Type: application/json
Accept: application/json
Cookie: <все текущие куки kliko.kz из приложения, в т.ч. гостевая сессия, если есть>
```

`Origin`/`Referer` приложение **не шлёт** (без поддельных источников) — источник для этого эндпоинта не проверять:
доказательство — подписанный Apple токен с `nonce`. Но `Content-Type` проверять обязательно (п. 0 ниже).
Перенаправления приложение **не выполняет**: любой ответ 3xx считается «сервер не поддерживает».

Тело (JSON):

| Поле                 | Тип    | Описание |
|----------------------|--------|----------|
| `identity_token`     | string | JWT от Apple (RS256). Главное доказательство. |
| `authorization_code` | string | Одноразовый код Apple (можно обменять на refresh token через `https://appleid.apple.com/auth/token`, нужен для отзыва доступа при удалении аккаунта). Может быть пустым. |
| `nonce`              | string | **Сырой** nonce (64 hex-символа). В токене лежит `sha256` от него. |
| `full_name`          | string | «Имя Фамилия» или пусто. |
| `given_name`         | string | Имя или пусто. |
| `family_name`        | string | Фамилия или пусто. |
| `email`              | string | Почта (может быть `…@privaterelay.appleid.com`) или пусто. |
| `user`               | string | `user` из Apple = `sub` токена. Только для сверки, **не доверять без токена**. |
| `bundle_id`          | string | `kz.kliko.app`. |
| `csrf`               | string | CSRF-токен страницы, если приложению удалось его прочитать. Может отсутствовать — для этого эндпоинта CSRF не обязателен (доказательство — подписанный Apple токен с nonce). |

### Обязательные проверки на сервере

0. **Только `Content-Type: application/json`** (параметры типа `; charset=utf-8` допустимы) — иначе
   `415` или `{"ok":false,"error":"bad_token"}`, сессию не трогать и `Set-Cookie` не отдавать. Это защита от подделки
   входа (login CSRF): чужая страница может отправить из браузера человека форму `enctype="text/plain"`, тело которой
   выглядит как JSON с **токеном злоумышленника**, — POST верхнего уровня браузер выполнит с кукой `SameSite=Lax`, и
   человек окажется в чужом аккаунте. Форма не умеет `application/json`, а `fetch` с ним с чужого сайта требует
   CORS-preflight — на этот эндпоинт **не отвечать** `Access-Control-Allow-Origin` (и на `OPTIONS` — без разрешений).
   Приложение всегда шлёт `application/json`.
1. Разобрать JWT, взять `kid` из заголовка, найти ключ в JWKS Apple `https://appleid.apple.com/auth/keys`
   (кешировать, при незнакомом `kid` — перечитать). Проверить подпись **RS256**. Алгоритм `none`/HS* — отказ.
2. `iss` == `https://appleid.apple.com`.
3. `aud` == `kz.kliko.app` (bundle id приложения; **не** Services ID сайта — у веб-входа `aud` другой).
4. `exp` > сейчас (допуск на часы — не больше 60 с); `iat` не из будущего.
5. `nonce` в токене == `hex(sha256(nonce из тела))` (строчные hex). Сравнение — `hash_equals`.
   Желательно помнить использованные `nonce` (или пару `sub`+`iat`) до истечения `exp`, чтобы тот же токен нельзя
   было предъявить второй раз.
6. Если `nonce_supported` в токене есть и равно `true` — nonce обязан совпасть (п. 5 выполняется всегда).
7. Пользователь ищется **по `sub`** (стабильный идентификатор Apple для нашей команды). Почта — только для
   заполнения профиля при создании, **не** для поиска существующего аккаунта (почта может быть скрытой, а чужой
   аккаунт по совпадению почты привязывать нельзя). `email_verified` учитывать, если почта используется.
8. `sub` уже привязан к аккаунту → вход в этот аккаунт. Не привязан → то же, что делает веб-колбэк Apple сейчас
   (создать аккаунт / попросить номер и т.д.) — логика та же, что у `apple_auth.php?action=start`.
9. После успешной проверки — `session_regenerate_id(true)` и установка той же куки сессии, что при обычном входе.

### Ответ

Всегда `Content-Type: application/json`, код 200 (кроме «не поддерживается», см. ниже).

**Успех:**

```json
{ "ok": true, "uid": "u0123456789ab" }
```

с заголовком `Set-Cookie` сессии — **то же имя, путь и домен, что при входе паролем** (`kliko_cab`, `Path=/`,
`Secure`, `HttpOnly`, `SameSite=Lax`). Приложение перекладывает эти куки в хранилище WebKit и перезагружает страницу
уже вошедшим. `uid` — идентификатор пользователя как в `cabinet.php?action=login` (можно пусто, но лучше отдавать).

**Отказы** (`ok: false`), приложение понимает те же поля, что у `cabinet.php?action=login`:

| Ответ | Что покажет приложение |
|-------|------------------------|
| `{"ok":false,"error":"unsupported"}` | Откроет прежнюю страницу `apple_auth.php?action=start` |
| `{"ok":false,"deleted":true,"reason":"…"}` | Окно «Аккаунт удалён» с причиной |
| `{"ok":false,"need_egov":true}` | Окно подтверждения входа через eGov (`cabinet.php?egov_confirm=1`) |
| `{"ok":false,"error":"Текст для человека"}` | Этот текст у кнопки Apple |
| `{"ok":false,"error":"bad_token"}` (машинный код `^[a-z][a-z0-9_]{1,14}$`) | «Ошибка входа» |

Рекомендуемые машинные коды: `bad_token` (подпись/iss/aud/exp), `bad_nonce`, `replay`, `rate_limited`.

**«Не поддерживается»** (приложение откатывается на страницу сайта): HTTP 404, 405, 501, любой 3xx,
не-JSON тело или `{"ok":false,"error":"unsupported"}`. Сейчас, пока эндпоинта нет, так и происходит.

## 2. Подключение Instagram / TikTok для автопостинга

### Проблема

`social_connect.php?platform=…&do=start` требует вход. Системный лист авторизации iOS
(`ASWebAuthenticationSession`) ходит с куками Safari, а не приложения — там человек не вошёл. Поэтому приложение
сначала получает **одноразовую ссылку** своей сессией, и лист открывает уже её.

### Шаг 1: `POST /social_connect.php?action=app_link`

Запрос делается изнутри страницы сайта в приложении (`fetch`, same-origin, с кукой сессии, настоящими Origin/Referer):

```
POST https://kliko.kz/social_connect.php?action=app_link
Content-Type: application/json

{ "platform": "instagram", "csrf": "<токен сессии>" }
```

- `platform` — `instagram` или `tiktok` (как в `cabinet.php?action=social_status`).
- `csrf` — тот же токен, что у остальных POST кабинета. На устаревший токен ответ `{"ok":false,"error":"csrf"}` —
  приложение перечитает токен и повторит один раз.
- Желательно принимать и `application/x-www-form-urlencoded` (`platform=instagram&csrf=…`) — на будущее.

Проверки: пользователь вошёл (иначе `{"ok":false,"error":"auth"}`), есть право на автопостинг (PRO), платформа
включена администратором.

**Успех:**

```json
{ "ok": true, "url": "https://kliko.kz/social_connect.php?platform=instagram&do=start&ott=<одноразовый токен>" }
```

Требования к `url`: схема `https`, хост `kliko.kz` или `www.kliko.kz` — иначе приложение считает ответ
неподдерживаемым и откатывается.

**Не поддерживается / отказ** — приложение делает прежнее (открывает страницу `social_connect.php?…&do=start`
внутри приложения): 404, не-JSON, перенаправление, `ok:false` с любым `error` (в том числе `"unsupported"`).

### Одноразовый токен (`ott`) — требования

- Случайный, **не меньше 128 бит** энтропии (`bin2hex(random_bytes(32))`).
- **Одноразовый**: помечается использованным при первом предъявлении (атомарно, `UPDATE … WHERE used=0`).
- **TTL ≤ 5 минут.**
- **Привязан к user id** (и к `platform`): хранить `ott_hash = sha256(ott)`, `user_id`, `platform`, `expires_at`,
  `used_at`. Сам токен в базе и в логах не хранить.
- Не логировать `ott` в access-логах (или маскировать query-параметр).

### Шаг 2: лист авторизации

Приложение открывает `url` в `ASWebAuthenticationSession` c `callbackURLScheme = "kliko"` и
`prefersEphemeralWebBrowserSession = true` (чистые куки, без Safari).

Сервер на `social_connect.php?…&do=start&ott=…`:

1. Проверяет `ott` (существует, не использован, не истёк, `platform` совпадает) и помечает использованным.
2. Заводит **временную** сессию подключения для этого `user_id` (только для OAuth-потока, не полноценный вход в
   кабинет) и ведёт на OAuth Instagram/TikTok как сейчас (`state` — как сейчас, привязан к этой сессии).
3. OAuth-колбэк сохраняет токены соцсети для `user_id` из шага 1.
4. В конце — **перенаправление только на**:

```
kliko://social_connected?platform=instagram&ok=1
kliko://social_connected?platform=instagram&error=<код или текст>
```

Никаких других адресов возврата (никаких `redirect_uri`/`return` из запроса) — открытое перенаправление запрещено.
В ссылку возврата не класть токены.

Приложение по `ok=1` покажет «Instagram подключён ✓», по `error` — текст (машинный код → «Не удалось подключить …»;
`access_denied`/`cancel` — молча), затем перечитает `cabinet.php?action=social_status`.

## 3. Вход через Google: `POST /google_auth.php?action=native`

Просьба владельца (13.10.2026): «регистрация по гуглу». В приложении — кнопка «Продолжить с Google» под кнопкой Apple
(Apple остаётся: правило App Store 4.8). Google SDK не используется.

### Как работает в приложении

1. Приложение генерирует `nonce` (32 случайных байта, hex, 64 символа), PKCE `code_verifier` (32 байта, base64url) и
   `state`, и открывает системный лист входа (`ASWebAuthenticationSession`) на
   `https://accounts.google.com/o/oauth2/v2/auth` с параметрами: `client_id` = iOS-клиент Google,
   `redirect_uri` = `com.googleusercontent.apps.<id>:/oauth2redirect` (обратный ID клиента), `response_type=code`,
   `scope=openid email profile`, `code_challenge` (S256), `state`, **`nonce` = `hex(sha256(nonce))`** (как у Apple),
   `prompt=select_account`, `hl` = язык телефона.
2. Код из возврата приложение **само** меняет на токены: `POST https://oauth2.googleapis.com/token`
   (`client_id`, `code`, `code_verifier`, `grant_type=authorization_code`, `redirect_uri`). У iOS-клиента секрета нет —
   это нормально для установленных приложений с PKCE. `access_token` приложение выбрасывает, серверу уходит только
   `id_token`.
3. `id_token` и сырой `nonce` уходят на сервер (URLSession, не из страницы).

### Запрос

```
POST https://kliko.kz/google_auth.php?action=native
Content-Type: application/json
Accept: application/json
Cookie: <все текущие куки kliko.kz из приложения, в т.ч. гостевая сессия, если есть>
```

`Origin`/`Referer` приложение **не шлёт** (без поддельных источников) — источник для этого эндпоинта не проверять:
доказательство — подписанный Google токен с `nonce`. Зато **`Content-Type` проверять обязательно** (п. 0 ниже): без
этого возможна подделка входа. Перенаправления приложение не выполняет: любой 3xx — «сервер не поддерживает».

Тело (JSON):

| Поле        | Тип    | Описание |
|-------------|--------|----------|
| `id_token`  | string | JWT от Google (RS256). Единственное доказательство. |
| `nonce`     | string | **Сырой** nonce (64 hex-символа). В токене лежит `sha256` от него. |
| `client_id` | string | ID iOS-клиента, которым получен токен. Только для журнала — сверять `aud` с **своим** списком, не с этим полем. |
| `bundle_id` | string | `kz.kliko.app`. |
| `csrf`      | string | CSRF-токен страницы, если приложению удалось его прочитать. Для `action=native` не обязателен (от подделки входа защищает п. 0); если пришёл — сверить с сессией. |

Имя и почту приложение **не присылает** — сервер берёт их из проверенного токена (`name`, `given_name`,
`family_name`, `email`, `email_verified`, `picture`).

### Обязательные проверки на сервере

0. **Только `Content-Type: application/json`** — иначе `415` или `{"ok":false,"error":"bad_token"}`, без
   `Set-Cookie` и без записи в сессию (в т. ч. без `google_pending`). Как у Apple (раздел 1, п. 0): токен под
   общедоступный iOS-клиент злоумышленник получает сам, и форма `enctype="text/plain"` с его токеном и его `nonce` с
   чужой страницы впустила бы человека в аккаунт злоумышленника (его объявления, переписка — злоумышленнику). Защита от
   повтора `nonce` тут не помогает. Форма не умеет `application/json`, `fetch` с ним требует CORS-preflight — на
   `google_auth.php` **не отвечать** `Access-Control-Allow-Origin`.
1. Подпись: `kid` из заголовка JWT → ключ из JWKS Google `https://www.googleapis.com/oauth2/v3/certs` (кешировать по
   `Cache-Control: max-age`, незнакомый `kid` — перечитать). Только **RS256**; `none`/HS* — отказ.
2. `iss` ∈ {`https://accounts.google.com`, `accounts.google.com`}.
3. `aud` == ID iOS-клиента (`GOOGLE_IOS_CLIENT_ID` в конфиге сервера). Если сайт когда-нибудь заведёт веб-вход
   Google — список разрешённых `aud` = {iOS-клиент, веб-клиент}, и больше ничего. Если в токене есть `azp` — он тоже
   должен быть из этого списка.
4. `exp` > сейчас (допуск на часы ≤ 60 с); `iat` не из будущего.
5. `nonce` в токене == `hex(sha256(nonce из тела))` (строчные hex), сравнение — `hash_equals`. Помнить использованные
   `nonce` до `exp` — повтор того же токена — отказ `replay`.
6. Пользователь ищется **по `sub`** — новая колонка `users.google_sub VARCHAR(255) NULL UNIQUE`.
7. **По почте к существующему аккаунту не привязывать никогда** — как у Apple (раздел 1, п. 7). Аккаунты Kliko
   заводятся по номеру (`register_quick`), а почту в профиль человек вписывает сам: опечатка или нарочно вписанный
   чужой Gmail отдал бы аккаунт владельцу этого Gmail — без номера и пароля. `email_verified` и
   `hd` говорят только о почте на стороне Google, а не о том, чья почта записана в профиле Kliko. Совпала почта или
   нет — человек идёт как новый (п. 8): шаг номера, а при занятом номере — `exists`. Google привязывается к
   существующему аккаунту только **из кабинета вошедшего** (вошёл номером и паролем → «Привязать Google»).
8. `sub` не найден → аккаунт **не создавать сразу**: номер телефона у Kliko обязателен. Положить
   ожидание в **текущую** сессию: `$_SESSION['google_pending'] = {sub, email, email_verified, name, given_name,
   family_name, picture, expires: now + 10 мин}` и ответить `need_phone` (ниже). Сессию здесь **не пересоздавать**:
   если кука сессии пришла с запросом, ID остаётся тем же (страница под приложением продолжит работать со своим
   CSRF); если куки не было — завести сессию и отдать `Set-Cookie`.
9. Аккаунт удалён / нужен eGov — те же признаки, что у `cabinet.php?action=login`.
10. Успех — `session_regenerate_id(true)` и та же кука сессии, что при входе паролем.

### Ответ `action=native`

Всегда `Content-Type: application/json`, код 200 (кроме «не поддерживается»).

| Ответ | Что сделает приложение |
|-------|------------------------|
| `{"ok":true,"uid":"u0123456789ab"}` + `Set-Cookie` сессии (`kliko_cab`, `Path=/`, `Secure`, `HttpOnly`, `SameSite=Lax`) | Куки — в хранилище WebKit, страница перезагружается вошедшей, витрина/чат/кабинет узнают сразу |
| `{"ok":false,"need_phone":true,"csrf":"<токен этой сессии>","email":"a@gmail.com","name":"Алия"}` | Шаг «Укажите номер» (ниже). `csrf` обязателен — с ним придёт `action=phone`. `email`/`name` — только показать, каким аккаунтом входят |
| `{"ok":false,"deleted":true,"reason":"…"}` | Окно «Аккаунт удалён» с причиной |
| `{"ok":false,"need_egov":true}` | Подтверждение входа через eGov (`cabinet.php?egov_confirm=1`) |
| `{"ok":false,"error":"Текст для человека"}` | Этот текст у кнопки Google |
| `{"ok":false,"error":"bad_token"}` (машинный код `^[a-z][a-z0-9_]{1,14}$`) | «Не удалось войти через Google — попробуйте ещё раз» |

Рекомендуемые машинные коды: `bad_token` (подпись/iss/aud/exp), `bad_nonce`, `replay`, `rate_limited`.

**Пробный запрос.** Открывая экран входа, приложение (если в сборке вписан iOS-клиент) один раз за запуск шлёт
`POST /google_auth.php?action=native` с телом `{}` и без кук. Сервер обязан ответить `200` и
`{"ok":false,"error":"bad_token"}` (не 500, не HTML) — так приложение узнаёт, что эндпоинт есть, и **только тогда
показывает кнопку Google**.

**«Не поддерживается»** — HTTP 404, 405, 501, любой 3xx, не-JSON тело или `{"ok":false,"error":"unsupported"}`:
кнопки Google нет; если это случилось посреди входа — «Вход через Google скоро заработает». Сейчас, пока эндпоинта
нет, так и происходит. Ответ 5xx без JSON — «Ошибка входа», кнопка остаётся.

### Шаг номера: `POST /google_auth.php?action=phone`

```
POST https://kliko.kz/google_auth.php?action=phone
Content-Type: application/json
Cookie: <куки приложения — та же сессия, где лежит google_pending>

{ "phone": "+7 (777) 123-45-67", "code": "", "csrf": "<csrf из ответа need_phone>", "agree": true }
```

- `phone` — значение поля с маской, как у `cabinet.php?action=register_quick`. Номер в поле приложение подставляет
  само: iOS предлагает номер этого iPhone, вставка в любом виде («8 777…», «+7(777)…», «77771234567») приводится к
  маске до отправки.
- `code` — пусто или цифры кода из SMS (если сервер его просил, см. `need_code`).
- `agree: true` — на экране под кнопкой «Продолжая, вы принимаете Пользовательское соглашение и Политику
  конфиденциальности» (как у кнопок соцвхода сайта). Записать принятие так же, как в `register_quick`.

Проверки:

0. Только `Content-Type: application/json` — как у `action=native` (п. 0): иначе `415` без записи в сессию.
1. CSRF сессии (`{"ok":false,"error":"csrf"}` — приложение перечитает токен и повторит один раз).
2. `google_pending` есть и не истёк — иначе `{"ok":false,"error":"expired"}` (приложение попросит войти через Google
   заново).
3. Номер Казахстана, код оператора — как `inc/phone_kz.php`; иначе `{"ok":false,"error":"bad_phone"}`.
4. **Номер уже у другого аккаунта** → `{"ok":false,"exists":true}`. Google к этому аккаунту **не привязывать**:
   владение Google-аккаунтом не доказывает владение номером. Приложение покажет окно «Номер уже зарегистрирован»
   (вход по паролю или восстановление через eGov). Привязку Google к существующему аккаунту — позже, из кабинета
   вошедшего.
5. **SMS — по желанию сервера.** Если сервер подтверждает номер кодом: первый запрос с пустым `code` → отправить SMS
   и ответить `{"ok":false,"need_code":true}`; приложение покажет поле кода (iOS подставит код из сообщения сама,
   поле помечено `oneTimeCode`) и пришлёт тот же запрос с `code`. Неверный код — `{"ok":false,"error":"bad_code"}`,
   лимит попыток — `rate_limited`. Если сервер SMS не шлёт (как `register_quick` сейчас) — `need_code` не отвечать
   никогда.
6. Создать аккаунт: номер, `google_sub`, почта (если `email_verified` и такой почты нет у другого аккаунта), имя. Пароль человеку не показывается —
   входит он через Google; задать пароль можно в кабинете. Очистить `google_pending`,
   `session_regenerate_id(true)`, кука сессии как при входе паролем.

Ответы `action=phone`: `{"ok":true,"uid":"…"}` + `Set-Cookie` — вошёл; `need_code`, `exists`, `deleted`,
`need_egov`, `error` (`expired`, `bad_phone`, `bad_code`, `csrf`, `rate_limited` или текст для человека) — как выше.

### Что вписать владельцу (по порядку)

1. **Сервер:** выложить `google_auth.php?action=native` и `action=phone`, колонку `google_sub`, в конфиг —
   `GOOGLE_IOS_CLIENT_ID` (п. 3). Проверить пробным запросом (раздел 4).
2. **Google Cloud Console** → APIs & Services → OAuth consent screen: название Kliko, почта поддержки, домен
   `kliko.kz`, ссылки на `https://kliko.kz/privacy.php` и `https://kliko.kz/soglashenie.php`, scopes
   `openid`, `email`, `profile`, статус **In production** (иначе войдут только тестовые аккаунты).
3. **Google Cloud Console** → Credentials → Create credentials → **OAuth client ID** → тип **iOS** → Bundle ID
   `kz.kliko.app` → Create. Скопировать **Client ID** вида `1234567890-abcdef….apps.googleusercontent.com`.
   Секрета у iOS-клиента нет — так и должно быть.
4. **Приложение — ID вписывается в двух местах `project.yml`** (цель `Kliko`, `info.properties`):
   - `KlikoGoogleClientID: "1234567890-abcdef….apps.googleusercontent.com"` — это и есть рубильник: пусто — кнопки
     нет;
   - в `CFBundleURLTypes` — вторая схема, обратный ID: `com.googleusercontent.apps.1234567890-abcdef…` (пример
     оставлен там комментарием). Лист входа ловит возврат и без неё, это подстраховка.
5. Тот же ID — в `GOOGLE_IOS_CLIENT_ID` на сервере (п. 1). Собрать сборку, проверить (раздел 4).

## 4. Как проверить

### Apple

1. Без изменений на сервере: кнопка «Войти через Apple» → лист Apple → после подтверждения приложение открывает
   прежнюю страницу `apple_auth.php?action=start` (откат работает).
2. Имитация отказа: `curl -i -X POST 'https://kliko.kz/apple_auth.php?action=native' -H 'Content-Type: application/json' -d '{}'`
   должно давать `200` и `{"ok":false,"error":"bad_token"}` (не 500, не HTML).
3. Проверки токена — модульными тестами на сервере: подменённая подпись, чужой `aud` (например Services ID сайта),
   истёкший `exp`, неверный `nonce`, повтор того же токена — все дают `ok:false`.
4. На устройстве (TestFlight): первый вход новым Apple ID — создаётся/привязывается аккаунт, приложение сразу
   вошедшее (кабинет, чат, избранное). Выход и повторный вход — тот же аккаунт (поиск по `sub`), имя/почта пустые — это
   нормально.
5. Убедиться, что после ответа `ok:true` в DevTools/логах сервера видна новая сессия и `Set-Cookie` с тем же именем
   куки, что при входе паролем.

### Соцсети

1. Без изменений на сервере: «Подключить Instagram» открывает страницу сайта, как раньше.
2. `app_link` без входа → `{"ok":false,"error":"auth"}`; с входом → `ok:true` и `url` с `ott`.
3. Открыть выданный `url` дважды — второй раз отказ (одноразовость). Подождать 6 минут — отказ (TTL).
4. Полный цикл на устройстве: лист → вход в Instagram → лист закрывается сам, в окне «Поделиться» кнопка становится
   «Опубликовать в Instagram (@имя)».
5. Отказ в OAuth (нажать «Отмена» у Instagram) → возврат `kliko://social_connected?platform=instagram&error=access_denied`,
   приложение ничего не показывает и просто обновляет статус.

### Google

1. Пока `KlikoGoogleClientID` в `project.yml` пустой — кнопки «Продолжить с Google» нет нигде (и запросов к Google и
   к `google_auth.php` приложение не делает).
2. Пробный запрос: `curl -i -X POST 'https://kliko.kz/google_auth.php?action=native' -H 'Content-Type: application/json' -d '{}'`
   → `200` и `{"ok":false,"error":"bad_token"}`. Пока так не отвечает — кнопки нет и со вписанным ID.
3. Проверки токена — модульными тестами на сервере: чужая подпись, чужой `aud` (например, веб-клиент другого
   проекта), истёкший `exp`, `iss` не Google, неверный `nonce`, повтор того же токена — все дают `ok:false`.
4. На устройстве (TestFlight): новый Google-аккаунт → лист Google → шаг «Укажите номер» (над клавиатурой iOS
   предлагает номер этого iPhone) → «Продолжить» → приложение вошедшее. Выход и повторный вход тем же Google — сразу
   вошедший (поиск по `sub`), без шага номера.
5. Шаг номера с номером, который уже есть у другого аккаунта → `exists:true` → окно «Номер уже зарегистрирован»,
   Google к чужому аккаунту не привязан. Google-аккаунт с той же почтой, что вписана в профиль другого аккаунта
   Kliko, — тоже шаг номера, а не вход в тот аккаунт.
6. Закрыть шаг номера и подождать 11 минут, повторить `action=phone` → `expired`.
7. Отмена в листе Google → приложение молча остаётся на экране входа.
8. Подделка входа: `curl -i -X POST 'https://kliko.kz/google_auth.php?action=native' -H 'Content-Type: text/plain' -d '{"id_token":"x","nonce":"y"}'`
   → `415` или `bad_token`, без `Set-Cookie`. То же для `action=phone` и `apple_auth.php?action=native`.
