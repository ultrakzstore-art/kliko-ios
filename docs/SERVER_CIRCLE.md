# «Круг вещей»: купил → пользуюсь → продал — что нужно от сервера

Документ для разработчика сайта kliko.kz (ultra-site), 16.10.2026, первая редакция. Продолжает
`docs/SERVER_STANDARDS.md` (§5 «что почём», §6 снимок сделки и «Куплено на Kliko», §7 «Новинки для моего») и
`docs/SERVER_MY_THINGS.md` (`fit_*` в теле POST, `fit_match`, «Моё» на телефоне) и ни одному из них не противоречит:
**поля и параметры только добавляются**, каждая часть включается своим флагом схемы — без новой сборки приложения. Что
уже есть в тех договорах, здесь не повторяется: только ссылка на §. Семьи стандартов —
`docs/SERVER_STANDARDS_catalog.json`.

Слова владельца, 16.10.2026:

> «Мой дом так же — что можно по дому? и что в “Моё” ещё добавить? = это нужно для рекомендаций — по этим параметрам
> новинки и прочее»; «мой компьютер — видюха или ОЗУ; подсказывать — можно так или так; и показывать, что был куплен
> там — короче, цифровизация реальности»; «Это разъёб будет да? Оттуда сразу продать?»; «тот же сборщик ПК уже внутри
> получается? + история покупок и продаж — связано?»; «так же и гардероб вещей»; «так же для ultra-site это»; «как это
> самое задание дашь, чтобы сервер на ultra-site уже был готов — для всех моментов».

## Суть

```
 найти подходящее ──► спросить продавца ──► купить: одна сделка ──► проверить при ──► вещь сама в «Моё»
 («Подходит»,         «Подойдёт?» (§9)      или сборка (§7),        получении           (галочка при
  «Новинки» §6)                             гарантия «Подходит» (§8)  (STANDARDS §6.2)  оплате, §2)
        ▲                                                                                    │
        │                                                                                    ▼
 следующий владелец ◄── «Продать своё» (§4): черновик ◄── пользуюсь: «что почём», подходящие новинки,
 видит «Куплено на Kliko    из сделки, цена по сделкам      история вещи и стоимость владения (§5)
 · 10.2026» — если продавец разрешил
```

На вопросы владельца:

- **«Оттуда сразу продать?»** — да: «Продать своё» из «Моего» — черновик подачи из сделки за одно касание (§4).
- **«Сборщик ПК уже внутри?»** — да: «Мой компьютер» и подсказки «можно так или так» (`docs/STANDARDS.md` §6.5, 8.1) +
  сборка (§7) — несколько безопасных сделок одной кнопкой, деньги у Kliko до получения каждой детали; детали
  сверяются между собой тем же каталогом.
- **«История покупок и продаж — связано?»** — да: покупка (сделка) → «Продать своё» (`relist_from`) → продажа (сделка).
  Цепочку и «стоимость владения» видит только владелец (§5).
- **«Так же для ultra-site»** — §12: «Моё» на сайте, «Продать своё», «что почём», сборки.

## 1. Общее и флаги

### 1.1. Совместимость

- Поля и параметры **только добавляются**. Старые сборки их не шлют и не читают, старый сервер молча игнорирует. Ни
  один прежний ответ не меняется; незнакомое значение приложение читает как отсутствие поля.
- Нет флага — нет функции: приложение делает то, что умеет на телефоне (`docs/STANDARDS.md` §8.8: «Куплено на Kliko»
  из снимка или `?id=`, «Продать своё» из снимка), и новых полей не шлёт.
- **Деньги.** Всё денежное в приложении — за рубильником `Config.деньгиСделок`: выключен — денежная кнопка открывает
  страницу сайта (`cabinet.php?deal=<id>`, для сборки — `cabinet.php?cart=<id>`, §12.4). Денежный POST приложение шлёт
  **ровно один раз**, без повторов на обрыв и таймаут (`Deals/DealMoneyAPI.swift`); от двойного списания сервер
  защищается сам (§7.4).
- **Пока гарант на паузе** (`MK_ESCROW_PAUSED` страницы) — `circle.cart`, `circle.fit_guarantee`, `circle.my_add`
  держать `false`.
- Адреса — как сейчас у приложения: `escrow.php`, `cabinet.php` — `/kz/<язык>/…` с куками и `csrf` полем JSON
  (`Deals/DealsAPI.swift`); `chat.php`, `subs.php` — от корня (`ListingChat/ListingChatAPI.swift`,
  `SavedSearch/SubsSync.swift`); `api/*` — от корня.
- Языки — `ru`, `kk`, `en`, `ar`. Тексты `error` — готовые, на языке запроса.

### 1.2. Флаги в схеме

```json
"rules": {
  "circle": { "on": true,
              "deal_item": false, "my_add": false, "grade": false, "relist": false, "chain": false,
              "saved_fit": false, "saved_fit_size": false, "cart": false, "cart_all": false, "cart_max": 10,
              "fit_guarantee": false, "fit_guarantee_kinds": ["std", "car", "phone", "laptop"],
              "fit_ask": false, "vin": false, "plate": false, "home": false, "wear": false,
              "fit_feedback": false, "site_my": false },
  "cond_grade": { "…": "§3.3" },
  "colors": { "…": "§11.2" },
  "fit_filters": { "…": "как раньше", "kids": false }
}
```

| Флаг | Ставить, когда работает | Что делает приложение |
|---|---|---|
| `circle.on` | общий рубильник блока: `true` — вместе с первым включённым флагом ниже | `false` или нет блока — все части круга считаются выключенными (выключить весь круг одним флагом) |
| `circle.deal_item` | дополнения снимка и сделки §2.2 (поверх `rules.std.deals`) | карточка купленного в «Моём» с состоянием и обложкой; смена итога после `sold` |
| `circle.my_add` | `my_add` в `create`, `cart_create`, `set_my_add` (§2.3) | галочка «Добавить в «Моё» после получения» в окне сделки |
| `circle.grade` | `cond_grade`, `batt_pct` в подаче, правке, выдаче (§3.1–3.3). Срез `grade` в ценах (§3.4) этого флага не ждёт — он идёт с «Что почём», приложение узнаёт его по эху `grade` в ответе | шкала состояния в подаче вместо «Новое / Б/у» |
| `circle.relist` | `relist_draft`, `relist_from`, `show_provenance`, `relisted_as` (§4) | «Продать своё» по черновику сервера; иначе — из снимка сделки сам |
| `circle.chain` | `item_chain` (§5.2) | история вещи из ответа сервера; иначе — собирает сама из `my_deals` и `my_items` |
| `circle.saved_fit` | `subs.php` с `kind: "fit"`, `notify`, `set`, `remove_kind`, `listings.php?sub=` (§6) | «Сообщать push-ом» у вещей гаража, устройств, дома, питомцев, хобби |
| `circle.saved_fit_size` | то же для `size` взрослых таблиц (§6.2) | то же у размеров одежды и обуви |
| `circle.cart`, `cart_max` | сборки в режиме `any` (§7) | «Добавить в сборку», «Оформить сборку» |
| `circle.cart_all` | режим `all` и `kit_ready` (§7.5) | переключатель «Всё или ничего» |
| `circle.fit_guarantee`, `fit_guarantee_kinds` | `fit_claim`, `nofit`, `return_fault: "platform"` (§8) | значок и галочка «Гарантия «Подходит»» у этих видов |
| `circle.fit_ask` | `fit_ask`, `fit_auto`, `fit_answer` (§9) | кнопка «Спросить продавца: подойдёт?» |
| `circle.vin`, `circle.plate` | `api/autofit.php` `vin`, `plate` (§10) | «Найти по VIN» / «по госномеру» в редакторе машины |
| `circle.home`, `circle.wear` | `knockdown`, `pass_cm`; `color`, `size_fit`, фильтр `color=` (§11.2) | поля в подаче; «Пройдёт ли?» и «С чем носить» по ним |
| `circle.fit_feedback` | `fit_feedback`, `brand_fit` (§11.3) | вопрос «Подошло?» уходит на сервер; строка про бренд у объявления |
| `circle.site_my` | раздел «Моё» на сайте (§12) | ничего нового: `?s=my` и `?go=my` и так открывают хаб «Моё» приложения (`Links/CabinetRouter.swift`). Флаг — признак для сайта: его push и письма могут вести в раздел, а не в кабинет |
| `fit_filters.kids` | `fit_kids` (§11.4), **только после решения владельца** | «Искать по всему сайту» в «Моих детях» |

Нет ключа или `false` — части нет. Выключить — флагом и сменой `v` схемы, без сборки.

### 1.3. Порядок флагов между собой

`circle.on` — вместе с первым включённым флагом круга; `circle.deal_item` — после `rules.std.deals`; метка «Куплено на
Kliko» в `relist` — после `rules.std.provenance`;
`circle.saved_fit` — после `rules.std.subs` (тот же push) и после записи «История поиска» в анкете App Privacy (§6.8);
подписки принимать только тех видов, чей фильтр уже работает (`rules.fit_filters.car`, `phone`, `laptop`, `std`);
`circle.cart`, `circle.my_add`, `circle.fit_guarantee` — не на паузе гаранта (у гарантии межгород — после решения
владельца о потолке, §8.4); `circle.cart_all` — после `circle.cart`. Остальные независимы.

## 2. Купленное → «Моё»: карточка купленного (`deal_item`)

### 2.1. Уже договорено

`SERVER_STANDARDS.md` §6.1: снимок `listing_snapshot` на момент создания сделки (`std`, `std_src`, `qty`, `parts`,
`storage`, `size_sys`, `size_all`, `dim_*`, `device_models`, `category`, `title`, `listing_id`, `warranty_days`) и
`outcome` (`sold`, `refunded`, `cancelled`) — обеим сторонам; запасной путь — `?id=` снятого объявления для покупателя
этой сделки. §6.2 — «Проверить при получении» и `std_mismatch`. Здесь не повторяем.

### 2.2. Дополнить (флаг `circle.deal_item`)

```json
"listing_snapshot": { "…": "как SERVER_STANDARDS.md §6.1",
                      "brand": "Kingston", "cond_grade": "good", "batt_pct": null, "color": null,
                      "img": "https://cdn.kliko.kz/…/0.jpg" },
"outcome": "sold", "outcome_at": "2026-10-14T14:02:00+05:00", "refund_part": 0,
"my_add": true,
"cart_id": "C-2041",
"fit_guarantee": { "on": true, "kind": "std", "by": "kliko" },
"relisted_as": "f7g8h9"
```

| Поле | Кому | Что |
|---|---|---|
| `brand`, `cond_grade` (§3), `batt_pct` (§3.2), `color` (§11.2) | обеим | на момент создания сделки; нет у объявления — `null` |
| `img` | обеим | обложка на момент сделки — карточка вещи у владельца, даже если объявление удалят. Если `product_img` в сделке уже хранится и не меняется вслед за объявлением — второго поля не нужно, скажите (§19). В «Продать своё» не переносится (§4.6) |
| `outcome_at` | обеим | когда наступил итог (или сменился) |
| `refund_part` | обеим | частичный возврат денег по спору, вещь осталась у покупателя, ₸. Итог остаётся `sold`; в «Моём» цена покупки = оплачено − `refund_part`. Нет такого у вас — `0` |
| `my_add` | только покупателю | §2.3 |
| `cart_id` | только покупателю | §7.5 |
| `fit_guarantee` | покупателю целиком; продавцу — только `{"on": true}` | §8 |
| `relisted_as` | только покупателю | §4.5 |

- **Итог может смениться.** Возврат по гарантии продавца (`warranty_days`, `warranty_ask`) или спор после `sold` →
  `outcome: "refunded"` и новый `outcome_at`. Приложение перечитывает `my_deals&role=buyer` при открытии «Моего» (не
  чаще раза в час) и сверяет итоги вещей с `src: deal`. Нового push не нужно — хватает нынешних `escrow_*`
  (`Deals/DealListingBack.swift` уже ловит закрытие).
- `my_deals` — те же поля, что `deal` (без тяжёлых: истории, доказательств), чтобы «Моё» не открывало каждую сделку.
- Сделки eGov (EDS) — по желанию тем же снимком; пока «Моё» берёт только гарант-сделки.

**Готово, когда:** у новой сделки в `deal` и `my_deals` есть поля таблицы; продавцу не уходят `my_add`, `cart_id`,
`relisted_as` и `fit_guarantee` сверх `on`. **Проба:** §16, блок «§2».

### 2.3. Галочка «Добавить в «Моё»» при оплате (Mercari)

В окне «Безопасная сделка» (приложение — `Deals/DealCreate.swift`; сайт — окно `?start_deal=`) и в сборке — флажок
**«Добавить в «Моё» после получения»**. По умолчанию выключен; приложение ставит его само, только если человек раньше
включил «Добавлять купленное само» (`docs/STANDARDS.md` §8.8) — его же согласие.

```
POST /kz/ru/escrow.php?action=create      { "csrf": "…", "product_id": "a1b2c3", "hold_type": "full", "my_add": 1, "…": "доставка как сейчас" }
POST /kz/ru/escrow.php?action=set_my_add  { "csrf": "…", "deal_id": "D-10293", "on": 0 }   → { "ok": true, "my_add": false }
```

- Только покупатель этой сделки; иначе `{ "ok": false, "error": "access" }`. В любом статусе и до 30 дней после итога.
- Хранится признаком сделки, больше ничего; не для рекомендаций, рекламы и аналитики со связью с человеком.
- Смысл для приложения: `outcome: "sold"` и `my_add: true` — вещь ложится в «Моё» без вопроса, с «Отменить»;
  `false` — один вопрос после первой такой покупки (`docs/STANDARDS.md` §8.8). Сайту — только флажок (раздел «Моё»
  сайта показывает купленное и так, §12.1).

| Ключ | ru | kk | en | ar |
|---|---|---|---|---|
| `my_add` | Добавить в «Моё» после получения | Алғаннан кейін «Менікі» бөліміне қосу | Add to My Things after receiving | أضِف إلى «أشيائي» بعد الاستلام |
| `my_added` | В «Моём»: {title} · куплено {date} | «Менікі» бөлімінде: {title} · {date} сатып алынды | In My Things: {title} · bought {date} | في «أشيائي»: {title} · اشتُري {date} |

**Готово, когда:** `create` с `my_add: 1` даёт `my_add: true` в сделке покупателя; `set_my_add` меняет его только
покупателю; продавцу поле не уходит; окно сделки на сайте показывает флажок. **Проба:** §16, «§2».

### 2.4. Возврат — вещь уходит из «Моего» сама

Логика — на телефоне (хранилища на сервере нет), от сервера — честный `outcome` и `outcome_at` обеим сторонам:

| Итог | У покупателя в «Моём» | У продавца (вещь была в его «Моём», «Продать своё») |
|---|---|---|
| `sold` | «Куплено на Kliko {дата} · {сумма}» | «Продано», событие `sold` |
| `sold` + `refund_part` | вещь остаётся, сумма = оплачено − часть | «Продано», сумма — `seller_get` |
| `refunded` (и после `sold`) | вещь уходит сама, событие `removed` в истории (причина — возврат) | вещь возвращается: «Вернулась по возврату», `state: in_use` |
| `cancelled` | не добавлялась | объявление снова живое — `for_sale` |

**Старое приложение** и сайт ничего из этого не читают — у них всё как было.

## 3. Единая шкала состояния `cond_grade` (Xianyu)

### 3.1. Шкала

Шесть ступеней, ключи навсегда, порядок — от лучшего. Сейчас у объявления только `condition: new | used` — шкала
уточняет его и сама задаёт `condition`.

| `cond_grade` | ru | kk | en | ar | `condition` |
|---|---|---|---|---|---|
| `new` | Новое, в упаковке | Жаңа, қаптамасында | New, sealed | جديد، في العبوة | `new` |
| `open_box` | Новое, вскрыто | Жаңа, ашылған | New, open box | جديد، عبوة مفتوحة | `new` |
| `like_new` | Как новое | Жаңадай | Like new | كالجديد | `used` |
| `good` | Хорошее | Жақсы | Good | جيد | `used` |
| `fair` | Заметные следы | Іздері байқалады | Visible wear | آثار استعمال واضحة | `used` |
| `parts` | На запчасти | Бөлшекке | For parts | لقطع الغيار | `used` + пометка «на запчасти» |

| `cond_grade` | Пояснение ru | kk | en | ar |
|---|---|---|---|---|
| `new` | Не вскрывали | Ашылмаған | Never opened | لم تُفتح |
| `open_box` | Не пользовались, комплект полный | Қолданылмаған, жиынтығы толық | Unused, complete | غير مستعمل، كامل |
| `like_new` | Пользовались недолго, следов нет | Аз қолданылған, ізі жоқ | Briefly used, no marks | استُعمل قليلًا، بلا آثار |
| `good` | Лёгкие следы, всё работает | Жеңіл іздер бар, бәрі жұмыс істейді | Light marks, fully working | آثار خفيفة، يعمل بالكامل |
| `fair` | Царапины, потёртости; всё работает | Сызаттар, ысқылау бар; бәрі жұмыс істейді | Scratches, scuffs; fully working | خدوش واهتراء؛ يعمل بالكامل |
| `parts` | Не работает или неисправно | Жұмыс істемейді немесе ақаулы | Not working or faulty | لا يعمل أو معطّل |

Где показывать: там же, где сейчас «Состояние» у товаров. Не показывать — у машин, недвижимости, услуг, работы,
аренды (`skip_cats`, §3.3).

### 3.2. Подача, правка, выдача

```json
{ "category": "smartphones", "title": "iPhone 13 128 ГБ", "condition": "used", "cond_grade": "good", "batt_pct": 87, "…": "…" }
```

| Поле | Формат | Что |
|---|---|---|
| `cond_grade` | ключ шкалы | слово продавца. `condition` выводится из него по таблице 3.1; разошлись — главнее `cond_grade`, `condition` хранить выведенный. Незнакомый ключ — поле игнорировать, подача проходит |
| `batt_pct` | целое 50…100 | здоровье аккумулятора, % («Настройки → Аккумулятор → Состояние»). Только `batt_cats` (§3.3); меньше 50 — не хранить |

- `edit_item`: поля нет — не трогать; `""` / `0` — снять. **Старое приложение** правит без `cond_grade`, но шлёт
  `condition`: пришёл `condition`, который не сходится с хранимым грейдом по таблице 3.1, а `cond_grade` нет — грейд
  снять (продавец поменял состояние по-старому, грейд устарел).
- Выдача: лента, `?id=`, `?ids=`, `my_items` — плоско; в `specs` пункты `{ "key": "cond_grade", "label": "Состояние",
  "value": "Хорошее — лёгкие следы, всё работает" }` и `{ "key": "batt_pct", "label": "Аккумулятор", "value": "87 %" }`
  (kk «Аккумулятор», en «Battery health», ar «صحة البطارية»).
- Старые объявления без грейда — как раньше, по `condition`. Из текста грейд **не угадывать**. Kliko AI грейд не
  ставит: это слово продавца.

### 3.3. В схеме: `rules.cond_grade`

```json
"cond_grade": { "on": true, "keys": ["new", "open_box", "like_new", "good", "fair", "parts"],
                "titles": { "good": "Хорошее" }, "hints": { "good": "Лёгкие следы, всё работает" },
                "condition": { "new": "new", "open_box": "new", "like_new": "used", "good": "used", "fair": "used", "parts": "used" },
                "skip_cats": ["…машины, недвижимость, услуги, работа, аренда — ваши ключи"],
                "batt_cats": ["smartphones", "tablets", "laptops", "smartwatches"] }
```

Подписи — на языке схемы. `rules.cond_grade` — справочник шкалы, а не рубильник: `on: false` значит то же, что нет
блока. Нет `rules.cond_grade` — приложение берёт таблицу 3.1 из своей сборки. Включает шкалу только `circle.grade: true`:
до него приложение `cond_grade` не шлёт.

### 3.4. «Что почём»: срез по состоянию

`api/price_stats.php` (GET и пакетный POST, `SERVER_STANDARDS.md` §5) принимает необязательный `grade`: срез
`pkey × cond × grade`. Меньше 3 продавцов с этим грейдом — считать без него, `widened: ["grade"]`. В ответе — эхо
`grade`. `cabinet.php?action=market_price` (§5.7 там же) — так же. Без `grade` — всё как раньше.

### 3.5. Сделка и споры

- `cond_grade` уходит в снимок сделки (§2.2). «Проверить при получении» (`SERVER_STANDARDS.md` §6.2) показывает «Продавец
  указал: Хорошее — лёгкие следы»; хуже — спор `notdesc` (уже есть: «Состояние, комплект или характеристики
  расходятся с карточкой»), грейд из снимка — заявление продавца.
- В «Продать своё» грейд из снимка предлагается, **но никогда не лучше** — продавец выбирает сам (§4.2).

**Готово, когда:** `submit` с `cond_grade` отдаёт его и выведенный `condition`; правка без поля не стирает; старая
правка с другим `condition` снимает грейд; `price_stats` с `grade` даёт срез или `widened`. **Проба:** §16, «§3».

## 4. «Продать своё»: `relist_from`

### 4.1. Откуда

| Источник | Кто может | Что берётся | Фото | Метка «Куплено на Kliko» |
|---|---|---|---|---|
| `deal:<id>` | покупатель этой сделки, итог `sold` | снимок сделки (§2) | только новые | по выбору продавца (`show_provenance`) |
| `listing:<id>` своё | автор (проданное, снятое, в архиве) | поля объявления | свои прежние — можно | если у того объявления была — наследуется по выбору |
| `listing:<id>` чужое | тот, у кого был чат с продавцом по этому объявлению (купил при встрече) | только факты: раздел, название, `std`, `qty`, `parts`, размеры, габариты, модели | только новые | нет (покупка не через сделку) |
| вещь «Моего» без источника | — | телефон собирает сам из вещи | — | нет; в `submit` по желанию `from: "my"` |

### 4.2. Черновик: `GET /kz/ru/cabinet.php?action=relist_draft&from=deal:D-10293&lang=ru`

```json
{ "ok": true, "from": "deal:D-10293",
  "draft": { "category": "ram", "title": "Оперативная память Kingston DDR4 SO-DIMM 8 ГБ 3200", "brand": "Kingston",
             "std": { "ram_module": { "gen": "DDR4", "form": "SO-DIMM", "gb": 8, "mts": 3200 } }, "std_src": "scan", "qty": 2,
             "parts": null, "storage": null, "size_sys": null, "size_all": null,
             "dim_w": null, "dim_h": null, "dim_d": null, "device_models": null, "fits_diag_max": null, "color": null,
             "cond_grade": "good", "condition": "used", "images": [], "description": "" },
  "provenance_ok": true, "month": "2026-10",
  "price": { "…": "ответ market_price со std — SERVER_STANDARDS.md §5.7, плюс sold" },
  "existing": null }
```

| Поле | Что |
|---|---|
| `draft.title` | из снимка, очищенное, как модерация названий: без телефонов, ссылок, «срочно», «торг», имени магазина |
| `draft.std`, `std_src` | как у источника: `std_src` прежний (`scan`, `title`…), в подаче остаётся; `text` и `tpl` — тоже остаются (не лучше «Проверьте») |
| `draft.cond_grade` | из снимка; приложение просит выбрать заново, лучше не ставит |
| `draft.images` | всегда `[]` у сделки и чужого объявления; у своего объявления — его фото |
| `draft.description` | всегда `""`: чужой текст не переносим (§4.6). Приложение предложит описание Kliko AI по `std`, как сейчас |
| `provenance_ok`, `month` | метку можно показать: сделка — этого человека, `sold`, не `refunded`; месяц `outcome_at` |
| `price` | §4.4 |
| `existing` | номер живого объявления, уже поданного из этого же источника, — приложение предложит «Открыть объявление» |

Ошибки: `access` (не ваша сделка, нет чата по чужому объявлению), `not_found`, `refunded`. Без адреса приложение
собирает черновик из снимка само (`SERVER_STANDARDS.md` §6.3) — адрес нужен прежде всего сайту и для одинаковой чистки
названия и цены.

### 4.3. Подача

```json
{ "category": "ram", "title": "…", "std": { "…": "…" }, "std_src": "scan", "qty": 2, "cond_grade": "good",
  "relist_from": "deal:D-10293", "show_provenance": true, "from": "my", "…": "фото, цена, город — как обычно" }
```

| Поле | Что |
|---|---|
| `relist_from` | `deal:<id>` или `listing:<id>` — связь для истории владельца (§5) и для `existing`. Проверка — по §4.1; не прошла — поле молча игнорировать, подача проходит |
| `show_provenance` | `true` — покупатели видят «Куплено на Kliko через безопасную сделку · 10.2026» (`SERVER_STANDARDS.md` §6.3). Только при `deal:` с итогом `sold`. По умолчанию `false` |
| `from` | `"my"` — подано из «Моего», только статистика; незнакомое — игнорировать |

- `from_deal` (`SERVER_STANDARDS.md` §6.3) остаётся и значит `relist_from: "deal:<id>"` + `show_provenance: true`.
  Пришли оба — главнее `relist_from` и `show_provenance`.
- **Одна связь — одно живое объявление.** По этому `relist_from` уже есть живое объявление — новое публикуется, но
  связь и метка у него не ставятся (вторая копия той же вещи); черновик заранее сказал `existing`.
- Итог сделки-источника сменился на `refunded` — метку с объявления снять, связь оставить (владельцу видна история).
- `edit_item`: `show_provenance: false` — снять метку; `relist_from` — поля нет: не трогать, `""` — снять связь.

### 4.4. Цена-подсказка (Swappa: по завершённым сделкам)

`price` в черновике — ответ `market_price` со `std`, `cond` и `grade` (`SERVER_STANDARDS.md` §5.7, §3.4 здесь), якоря
в таком порядке:

1. **Как продавали через Kliko** — `sold` по `pkey` и `cond` при ≥ 5 сделках: «середина 10 500 ₸ · 6 сделок · 90 дней».
2. **Сейчас продают** — P25–P75 при ≥ 8 продавцах, «от–до» при 3–7, «от» — с одного (пороги §5.4 там же).
3. Срез `grade` — если в нём ≥ 3 продавца.

Цена прежней покупки — не якорь и в ответе сервера не нужна (владелец видит её у себя на телефоне). Тексты — честные
(`SERVER_STANDARDS.md` §5.8): ни «выгодно», ни «продайте быстрее».

### 4.5. Выдача

- Публично (лента, `?id=`): только `provenance: { "kliko": true, "month": "2026-10" }` при `show_provenance`
  (`SERVER_STANDARDS.md` §6.3). `relist_from` — **никогда**.
- `my_items` (владельцу): `relist_from`, `show_provenance`.
- Покупателю в `deal` и `my_deals`: `relisted_as` — номер последнего объявления с `relist_from: "deal:<эта>"` (живого или
  проданного). Так телефон связывает покупку с продажей.

### 4.6. Фото и текст

- Фото и описание прежнего продавца не переносятся никогда: это его работа (Закон РК «Об авторском праве и смежных
  правах») и его экземпляр. Переносятся только факты — раздел, стандарты, размеры, модель.
- Своё прежнее объявление — свои фото можно.
- Приложение сразу открывает план съёмки и студию (`Posting/PhotoStudio*`).

**Готово, когда:** черновик сделки — без фото и текста, с `provenance_ok`; чужой — `access`; подача с `relist_from` и
`show_provenance` даёт публичный `provenance` без `relist_from`, в `my_items` — связь, в сделке покупателя —
`relisted_as`; вторая подача из того же источника — без связи. **Проба:** §16, «§4».

## 5. История вещи и стоимость владения

### 5.1. Связи — всё уже на сервере

```
сделка D1 (я покупатель, sold) ──relisted_as──► объявление L2 (relist_from: deal:D1) ──► сделка D2 (я продавец, sold)
```

Телефон собирает историю сам: `my_deals&role=buyer` (`relisted_as`) → `my_items` (`relist_from`) →
`my_deals&role=seller` (сделка по L2: `outcome`, `seller_get`). Видит **только владелец**. Следующий владелец видит
только метку «Куплено на Kliko · месяц», если продавец разрешил; цепочки прежних владельцев не показываются никому.

### 5.2. `GET /kz/ru/escrow.php?action=item_chain&deal=D-10293` — для сайта (приложению по желанию)

```json
{ "ok": true, "chain": [
    { "ev": "bought", "at": "2026-02-12", "deal": "D-10293", "listing": "a1b2c3", "title": "…",
      "goods": 25000, "buyer_fee": 500, "ship": 1200, "points": 0, "refund_part": 0, "paid": 26700 },
    { "ev": "listed", "at": "2026-10-01", "listing": "f7g8h9", "price": 20000 },
    { "ev": "sold", "at": "2026-10-09", "deal": "D-11877", "goods": 19000, "seller_fee": 950, "seller_get": 18050 } ],
  "own_months": 8, "own_cost": 8650 }
```

- Только если спрашивает покупатель D1; иначе `access`. Только свои звенья: своя покупка, своё объявление, своя продажа.
- `paid` — фактически оплаченное (`actual_pay`) минус `refund_part`; `own_cost` = `paid` − `seller_get` (не продано —
  `null`); `own_months` — от `outcome_at` покупки до `outcome_at` продажи или до сегодня.

### 5.3. Как показываем

«Владение обошлось в 8 650 ₸ за 8 месяцев (≈ 1 100 ₸ в месяц)» — только владельцу, в истории вещи на телефоне и в «Моём»
сайта. Не продано — «Сколько стоит сейчас?» по нажатию (`price_stats`). Без оценок «вы потеряли», рейтингов и сравнений
с другими людьми. Покупки не на Kliko (чек ОФД, вручную) — только на телефоне (`docs/STANDARDS.md` §8.8).

### 5.4. «Сколько стоит всё моё» (Mercari)

Решение владельца (`docs/STANDARDS.md` §13): по умолчанию не показывать; по нажатию — на телефоне, пакетом
`POST api/price_stats.php` (`SERVER_STANDARDS.md` §5.3, по 20 запросов), не чаще раза в сутки. Серверу нового не нужно.

**Готово, когда:** `item_chain` отдаёт три звена владельцу и `access` — другим. **Проба:** §16, «§4».

## 6. «Новинки для моего»: сохранённый подбор (`saved_fit`)

### 6.1. Уже договорено

`SERVER_STANDARDS.md` §7: шаг А — локальные уведомления на телефоне; шаг Б — `subs.php?action=add` со `std` (публичный
фильтр одной вещи) и `label`, push не чаще раза в день, тишина 22:00–09:00, одно сообщение, только `ok` и `adapt`,
удаление вместе с сохранёнными поисками (`rules.std.subs`). `SERVER_MY_THINGS.md` §3.1: «`fit_*` в subs не принимать».

### 6.2. Что добавляется (флаг `circle.saved_fit`)

- Подписки «Новинок» помечаются **`kind: "fit"`** — и со `std` (§7.2 там же), и новые ниже. Обычные сохранённые
  поиски — `kind: "search"` (по умолчанию, как сейчас). У `fit` — свой дневной лимит, свои настройки, своё «удалить
  всё».
- Остальные виды «Моего» — по тому же явному нажатию «Сообщать push-ом» у вещи: `fit_car`, `fit_phone`, `fit_laptop` —
  ровно в формате тела POST ленты (`SERVER_MY_THINGS.md` §3.2–3.4); `size` — только взрослые таблицы
  (`SERVER_MY_THINGS.md` §3.5) и только при `circle.saved_fit_size`; дом, питомцы, хобби, компьютер — `std` семей с
  `fit_std: true`.
- Запрет `SERVER_MY_THINGS.md` §3.1 **остаётся** для `add` без `kind: "fit"`: обычный поиск `fit_*` не принимает.
- Никогда: `fit_me`, `fit_kids`, вещи «Моих детей», семьи `fit_std: false` (тело, вес, рост).

### 6.3. Запросы (от корня, куки, `csrf` — как у `subs.php` сейчас)

```

                                     "fit_car": "pcd:5x114.3;dia:60.1;et:35..45;r:16,17;tyre:205/55R16", "fit_level": "parts",
                                     "label": "Шины и диски 5x114.3 R16", "push": 1 }
```

| Поле | Что |
|---|---|
| `kind` | `fit` — «Новинки для моего»; нет поля — обычный поиск, как раньше. Подписка со `std` — всегда `fit` (сервер ставит сам, даже если `kind` не пришёл) |
| `kinds` (в `list`) | `search,fit` — отдать и подписки `fit`. **Без `kinds` — как сейчас, только обычные поиски**: установленные сборки забирают `list` в свой список (`SavedSearch/SubsSync.swift`, этап 36) и сами проверяют его в фоне по `keyword`, `category`, `city` (`SavedSearchCheck.swift`) — подписку `fit` они проверяли бы по всему разделу, без подбора; нынешняя витрина сайта показала бы её обычным поиском |
| `std`, `fit_car`, `fit_phone`, `fit_laptop`, `size` | **один** вид на подписку (одна вещь). Пришло несколько — оставить первый в этом порядке |
| `fit_level` | `parts` (по умолчанию — «Подходит» и «Нужна деталь») или `ok`. `check` не принимать |
| `label` | только стандарт, ≤ 60 знаков, обрезать; имён вещей «Моего» приложение не кладёт |
| `push` | `1` — присылать (по умолчанию у `kind: fit`: такую подписку создаёт только нажатие «Сообщать push-ом» у вещи); `0` — только в списке |
| `paused` | `null` · `"user"` · `"stale"` (§6.7) |
| `fit.daily` | `1` или `0`; больше 1 не бывает — обрезать до 1 |
| `fit.quiet` | часы тишины `[с, до]` по `tz`. Принимать только **шире** 22–9 (раньше начало, позже конец) |
| `fit.pause_until` | дата — до неё не присылать |

До 20 подписок `kind: fit` на аккаунт; сверх — `{ "ok": false, "error": "limit" }` с готовым текстом. Ни одного
принимаемого вида (пришёл только `fit_me`, `fit_kids` или ничего) — `{ "ok": false, "error": "fit_empty" }`. Гость —
только шаг А на телефоне (`need: "auth"`, как сейчас).

### 6.4. Отбор и отправка

- Проверка новых объявлений — ваша, как часто удобно; **push — не чаще одного в сутки на человека по всем `kind: fit`
  вместе**, вне тишины 22:00–09:00 по Алматы (UTC+5), одно сообщение на все находки.
- **Нынешняя мгновенная рассылка `sub`** (уведомление на каждое одобренное объявление, `url …&src=ss`,
  `inc/listing_approved.php` — ваш `APP_CHANGES.md` 29.09) подписки `kind: fit` **не берёт**: их значения она не
  сверяет и прислала бы весь раздел, и не по одному в сутки. Им — только дневная сводка `fit_new` (§6.5).
- В находки — опубликованные после `last_sent_at` (или создания подписки), прошедшие модерацию, с `fit_match` по
  `fit_level` подписки (`ok`; при `parts` — ещё «нужна деталь»: `adapt`, у машины `rings`, `spacers`, `rings+spacers`) по
  правилам `SERVER_MY_THINGS.md` §3 и `SERVER_STANDARDS.md` §4.3–4.4. Из текста (`std_src` / `compat_src: "text"`) —
  нет: это «Проверьте».
- Не своё объявление; одно объявление в одной подписке — один раз за всю её жизнь (`subs_seen`, §6.9); ТОП — на общих
  основаниях, без подъёма; город подписки (пустой — весь Казахстан).
- Нет находок — нет push. Никогда «загляните, у нас новое».

### 6.5. Push

```json

           "thread-id": "fit_new", "category": "FIT_NEW", "sound": "default" },
```

- Текст — из `label` и цен, на языке аккаунта; имён вещей нет (их нет и на сервере). Заголовок: «Новинки для моего» ·

- `url` — лента первой подписки (§6.6); старое приложение откроет её как страницу сайта — сайту понимать `?sub=`.

### 6.6. `api/listings.php?sub=<id>`

- С куками владельца сервер применяет **сохранённый фильтр подписки** (в адресе — только номер, значений «Моего» в
  журнале доступа нет), отмечает `last_open_at`. Не владелец или нет такой — параметр игнорировать (обычная лента), в
  `fit_applied` не входит.
- Ответ — как с `fit_*`: `fit_applied: ["sub"]`, `fit_match`; `Cache-Control: private, no-store`.

### 6.7. Отписка, срок жизни, удаление

- Одна подписка — действием в push, в списке «Сохранённые поиски», в карточке вещи «Моего». Все — `notify { daily: 0 }`
  (подписки остаются) или `remove_kind` (удалить все).
- 120 дней без открытия — `paused: "stale"`, push не идёт, в списке «Приостановлено — давно не открывали» с кнопкой
  «Включить» (`set { push: 1 }`). 365 дней без открытия — удалить. Никаких уведомлений «вернуть подписку?».
- Удаление аккаунта — вместе со всем. Выход на телефоне стирает «Моё» на телефоне, подписки остаются в аккаунте (видны
  в «Сохранённых поисках» сайта и приложения, которые просят `list&kinds=search,fit`; прежним сборкам они не отдаются,
  §6.3).

### 6.8. Приватность и App Privacy

- Подписки `kind: fit` — данные, **связанные с аккаунтом**: в анкете App Privacy это «История поиска» (Search History),
  цель — функциональность приложения, не трекинг. Сейчас её нет ни в анкете, ни в `Privacy/Kliko/PrivacyInfo.xcprivacy`
  (там: контакты, идентификаторы, место, фото, аудио, покупки, поддержка, прочее содержимое, скорость и сбои).
  **До `circle.saved_fit` владелец добавляет «Search History — Linked — App Functionality»** — заодно за обычные
  сохранённые поиски, которые сервер хранит уже сейчас.
- Не для рекламы, рекомендаций и ТОП; в аналитику — только счётчики без значений; в журналах — только номер подписки.
- Человек видит всё, что хранится, в своём списке (право на доступ — Закон РК «О персональных данных и их защите»).

## 7. Сборки: несколько безопасных сделок одной кнопкой (`cart`)

### 7.1. Суть

- **Сборка = несколько обычных безопасных сделок**, созданных и оплаченных одной кнопкой. Каждая деталь — своя сделка:
  свой продавец, своя передача, своё «Подтвердить получение», свой спор, свой возврат. Деньги каждой детали у Kliko до
  её получения.
- Примеры: ПК (процессор, плата, ОЗУ, БП — четыре продавца), кухня (посудомойка 45 + духовка + варочная), колёса
  (шины + диски + кольца).
- Корзина до создания живёт на телефоне или в `localStorage` сайта; на сервере — только созданная сборка.
- Только товары (не услуги, не аренда, не задаток) с гарантом. Физический товар — оплата вне Apple допустима (App Review
  3.1.3(e)); в приложении — за `Config.деньгиСделок` (§1.1).

### 7.2. `POST /kz/ru/escrow.php?action=cart_check` — только чтение

```json
{ "items": [ { "product_id": "a1b2c3" }, { "product_id": "x9y8z7" }, { "product_id": "d4e5f6" } ], "city": "Алматы" }
→ { "ok": true,
    "items": [ { "product_id": "a1b2c3", "ok": true, "price": 18000, "buyer_fee": 360, "seller_id": "77", "city": "Алматы" },
               { "product_id": "x9y8z7", "ok": true, "price": 42000, "buyer_fee": 840, "seller_id": "91", "city": "Алматы" },
               { "product_id": "d4e5f6", "ok": false, "why": "reserved" } ],
    "total": { "goods": 60000, "fees": 1200, "pay": 61200 }, "sellers": 2,
    "compat": [ { "a": "a1b2c3", "b": "x9y8z7", "level": "no", "why": "ram_module.gen: DDR5 ≠ DDR4 платы" } ] }
```

- Куки — чтобы узнать покупателя (своё объявление — `own`); `csrf` не нужен (если `escrow.php` требует его у любого
  POST — примите, приложение пришлёт). Доставка в `total` не входит — она у каждой детали своя (§7.7).
- `why`: `sold`, `reserved`, `gone`, `own`, `no_escrow`, `not_goods`, `price_changed` (+ новая `price`),
  `seller_paused`, `limit`.
- `compat` — **по желанию**: попарная сверка `std` деталей между собой по правилам `SERVER_STANDARDS.md` §4.4 (ОЗУ ↔
  плата, процессор ↔ плата, видеокарта ↔ корпус и БП, кулер ↔ сокет, шина ↔ диск). Нет поля — приложение считает само;
  сайту без него сборка тоже работает, но без проверки.

### 7.3. `POST /kz/ru/escrow.php?action=cart_create`

```json
{ "csrf": "…", "ikey": "6f1c2b9e-0b7a-4c1d-9a55-3e2f8d1c7b40",
  "items": [ { "product_id": "a1b2c3", "ship": "yandex", "ship_q": "q_81…" },
             { "product_id": "x9y8z7", "ship": "carrier", "ship_q": "q_93…", "car_pvz": "ALM-12" } ],
  "to_addr": "Алматы, …", "to_lat": 43.2389, "to_lon": 76.8897, "to_door": { "…": "как в create" },
  "kind": "pc", "label": "Сборка ПК · 2 детали", "mode": "any", "my_add": 1,
  "fit_claims": { "a1b2c3": { "kind": "std", "need": "…", "level": "ok", "v": "2026-10-16-1" } }, "from": "my" }
→ { "ok": true, "cart": { "id": "C-2041", "mode": "any", "status": "created", "deadline_left": 3600, "total_pay": 61200,
      "deals": [ { "id": "D-11001", "product_id": "a1b2c3", "total_pay": 18360, "fit_guarantee": { "on": true } },
                 { "id": "D-11002", "product_id": "x9y8z7", "total_pay": 42840, "fit_guarantee": null } ] } }
```

- Создаёт N сделок **ровно так, как `create` с `hold_type: "full"`** создал бы каждую: те же сборы, условия,
  верификация, бронь объявления, доставка (адрес общий, способ — у детали: `ship`, `ship_q`, `car_pvz` — как сейчас в
  `create`, `Deals/DealCreateShip.swift`).
- **Всё или ничего при создании**: не прошла хоть одна деталь — не создаётся ничего, `{ "ok": false, "error": "items",
  "items": [ { "product_id", "why" } ] }`; приложение предложит убрать их и повторить. Цена доставки устарела —
  `why: "ship_quote"`, как у `create`.
- `ikey` — UUID клиента: тот же `ikey` в течение суток → та же сборка (`exists: true`), второй не будет.
- `need_terms`, `need_verification` — как у `create`.
- `kind` (`pc`, `kitchen`, `wheels`, `home`, `wear`, `other`) и `label` (≤ 60, без имён «Моего») — для списка и
  статистики. `my_add` (§2.3) — на все сделки; `fit_claims` — по деталям (§8). `from` — статистика.
- 2…`cart_max` деталей; у покупателя одна неоплаченная сборка за раз — иначе
  `{ "ok": false, "error": "cart_open", "id": "C-…" }`.
- Не оплачено до срока брони — все сделки сборки истекают вместе.

### 7.4. Оплата: одной суммой или по отдельности

```
POST /kz/ru/escrow.php?action=cart_pay       { "csrf": "…", "cart_id": "C-2041", "use_points": 1 }  → { "ok": true, "cart": { "status": "paid", "…": "…" } }
POST /kz/ru/escrow.php?action=cart_pay_card  { "csrf": "…", "cart_id": "C-2041" }                   → { "ok": true, "url": "https://…банк…" }
```

- **Кошелёк:** одно списание всей суммы (за вычетом баллов), разнесённое по сделкам **в одной транзакции БД**: оплачены
  все или ни одна; не хватает — `{ "ok": false, "error": "low_balance", "need": 12400 }`.
- **Карта:** одна страница банка на сумму — по тому же правилу, что `pay_card` одной сделки (вся сумма или недостающее).
  Возврат `?topup=ok&cart=C-2041` → `pay.php?action=confirm` (как сейчас) → деньги на кошельке → сервер сам оплачивает
  все ещё живые сделки сборки. Сделка отменилась, пока шла оплата, — её доля остаётся в кошельке («вернулось в кошелёк»).
- Баллы (`use_points`) — по сделкам по порядку, как сайт считает у одной сделки.
- **По отдельности**: каждую сделку сборки можно оплатить обычным `pay` / `pay_card` — статус сборки `partial`, потом
  `paid`.
- **Двойное списание исключено сервером:** `cart_pay` оплаченной сборки → `{ "ok": true, "already": true }`;
  параллельные — блокировка строки сборки. Приложение денежный POST не повторяет никогда.

### 7.5. Жизнь сборки

```
GET /kz/ru/escrow.php?action=cart&id=C-2041
→ { "ok": true, "cart": { "id": "C-2041", "kind": "pc", "label": "…", "mode": "any", "status": "paid",
      "created_at": "…", "total_pay": 61200, "paid": 61200, "refunded": 0, "deals": [ { "…": "как в my_deals" } ] } }
```

- Только покупателю. `status`: `created` · `partial` · `paid` · `done` (все сделки закрыты) · `cancelled`.
- В `deal` и `my_deals` — `cart_id`, `cart_kind`, `cart_label` **только покупателю**; продавец видит обычную сделку (в
  режиме `all` — ещё `kit`, ниже). **Старое приложение** видит обычные сделки — всё работает.
- **Режим `all` — «всё или ничего»** (ПК, колёса; флаг `circle.cart_all`). После оплаты передача ни одной детали не
  начинается (курьер не вызывается, коды встречи и посылки не выдаются), пока **каждый** продавец не отметил «Готов
  передать»:

  ```
  POST /kz/ru/escrow.php?action=kit_ready { "csrf": "…", "deal_id": "D-11001" } → { "ok": true, "kit": { "n_ready": 3, "of": 4 } }
  ```

  В `deal` обеим сторонам — `kit: { "mode": "all", "ready": false, "n_ready": 3, "of": 4, "left": 52000 }`. Любое
  действие передачи продавца в этом режиме (вызов курьера, код встречи, трек) **засчитывается как «Готов»** и получает
  ответ `{ "ok": false, "error": "kit_wait" }` с готовым текстом «Ждём готовности остальных продавцов сборки» — так
  работает и старое приложение. Все готовы — передачи идут как обычно. Кто-то отказался или 24 часа без ответа — **все
  сделки сборки отменяются, деньги покупателю полностью**, вины покупателя нет; у промолчавшего продавца — обычные
  последствия отмены.

### 7.6. Отмена части, возвраты, споры

- Каждая сделка — свой `cancel`, как сейчас. Отменилась одна (продавец, бронь, покупатель до передачи) — её деньги
  возвращаются как у одной сделки; остальные идут дальше (режим `any`).
- После сбоя любой детали у покупателя 24 часа, чтобы **без штрафа** отменить ещё не переданные:

  ```
  POST /kz/ru/escrow.php?action=cart_cancel { "csrf": "…", "cart_id": "C-2041", "deal_ids": ["D-11002"], "reason": "kit_broken" }
  ```

  Сбор не удерживается, продавцам не в вину. Без `deal_ids` — все неоплаченные или не переданные. После передачи —
  только правила возврата.
- Возвраты и споры — **по каждой сделке**, как сейчас (`clocal_return_reason`, `dispute`); спор по одной не замораживает
  остальные. Гарантия «Подходит» — по каждой (§8).
- Возврат части одной оплаты картой: шлюз умеет частичный возврат — на карту; нет — на кошелёк с обычным выводом
  (вопрос §19).
- Push — одно сообщение на событие: «Деталь сборки отменена: 32 000 ₸ вернулись в кошелёк. Остальные 3 — в пути».
  Приложение предложит «Найти замену по стандарту» (поиск по `std` этой детали — на телефоне).

### 7.7. Доставка

У каждой сделки своя, как сейчас. Несколько деталей одного продавца — по желанию `ship_group`: один курьер на несколько
сделок (вопрос §19). Без него — раздельно.

|---|---|
| `items` | создание: хоть одна деталь не прошла, список с `why` |

### 7.9. Хранение (пример)

```sql

  label VARCHAR(60) NULL, mode ENUM('any','all') NOT NULL DEFAULT 'any', status VARCHAR(12) NOT NULL,

ALTER TABLE escrow_deals ADD COLUMN cart_id VARCHAR(16) NULL, ADD COLUMN kit_ready_at DATETIME NULL, ADD KEY k_cart (cart_id);
```

продавцу; отмена одной сделки не трогает остальные; `kit_wait` держит передачу в режиме `all`. **Проба:** §16, «§7»;
оплата — руками в тестовом кошельке.

## 8. Гарантия «Подходит» (eBay Guaranteed Fit)

### 8.1. Когда действует — все условия вместе

1. Приложение показало «Подходит» (`ok`) к вещи «Моего», человек оставил галочку «Гарантия «Подходит»» — подбор
   уходит в сделку (`fit_claim`, §8.2).
2. Сервер пересчитал по снимку объявления и `need` — получилось `ok` (не `adapt`, не `check`) по правилам
   `SERVER_STANDARDS.md` §4.4 и `SERVER_MY_THINGS.md` §3.2–3.4. Правила нет — гарантии нет (`why: "no_rule"`).
3. Значения у объявления — от продавца (`std_src` `""`, `title`, `scan`, `ai`, `model`; `compat_src` `""`), не из текста
   (`text`) и не примерные (`tpl`).
4. Вид — из `fit_guarantee_kinds`: `std`, `car`, `phone` (только `ok`, не `universal`), `laptop`. **Не действует:**
   размеры одежды и обуви (посадка субъективна), семьи тела, веса и роста (`fit_std: false`), безопасность
   (`safety: true` каталога — автокресла, матрасы в кроватку, возраст игрушек, цоколи ламп, вилки, кабель, блоки
   питания ПК, аккумуляторы машин, газ, диски болгарки), вещи «Моих детей», семьи с `max_level: "check"`. Колёсные
   диски и шины (`car`) — действует.
5. Товар через гарант; подбор сохранён до оплаты.

### 8.2. `fit_claim` в `create` и `cart_create`

```json
POST /kz/ru/escrow.php?action=create
{ "csrf": "…", "product_id": "a1b2c3", "hold_type": "full",
  "fit_claim": { "kind": "std", "need": "ram_module.gen:DDR4;ram_module.form:SO-DIMM;ram_module.max_gb:32",
                 "level": "ok", "v": "2026-10-16-1", "line": "DDR4 SO-DIMM · до 32 ГБ" } }
→ { "ok": true, "deal": { "id": "D-11003", "fit_guarantee": { "on": true, "kind": "std", "by": "kliko" } } }
```

- `need` — формат тела ленты: одна группа `fit_std` без `|`, либо `fit_car`, `fit_phone`, `fit_laptop`.
- Решение — в `deal.fit_guarantee`: `on`, а при `false` — `why` (`no_rule`, `level`, `src_text`, `safety`, `kind`,
  `limit`, `intercity`). Приложение до оплаты покажет «Гарантия не применилась: …» — человек может не платить.
- Хранится в сделке (данные покупки — «История покупок», уже в анкете). Видят покупатель и модератор; продавец — только
  «Покупка с гарантией «Подходит»», без `need`.
- **Чат-путь** (§9.3): продавец ответил «Подходит» на вопрос `fit_ask` — `fit_claim.by: "seller_chat"` и `msg_id` →
  гарантия с ответственностью продавца.

### 8.3. Возврат «Не подошло»: кто платит

Новая причина возврата `nofit` (к `clocal_return_reason`: `defect`, `wrong`, `notdesc`, `size`, `changed` —
`Deals/DealReturnBuyer.swift`) и спора `nofit` (к `defect`, `wrong`, `notdesc`, `missing`, `damaged`, `other` и
`std_mismatch`). Значение `ship_payer: "platform"` у вас уже есть (`Deals/DealMoneyAPI.swift` его читает).

| Что выяснилось | `return_fault` → `ship_payer` | Покупателю | Продавцу |
|---|---|---|---|
| вещь соответствует объявлению, «Моё» покупателя верное — **ошиблось правило Kliko** | `platform` → `platform` | всё оплаченное, вместе с доставкой туда | вещь назад, сбор не удерживается, доставку не платит |
| вещь не соответствует стандарту объявления | `seller` (как `notdesc`, `std_mismatch`) | всё | доставка туда и обратно, как сейчас |
| продавец ответил «Подходит» в чате (§9.3), «Моё» верное | `seller` | всё | как выше |
| в «Моём» было неверно (указано DDR5, а стоит DDR4) | `buyer` (как `size`, `changed`) | за вычетом доставки | обычный возврат |
| гарантии нет (`fit_guarantee.on: false`) | по обычным причинам | | |

- До решения модератора: причина `nofit` при гарантии → сразу `return_fault: "platform"`, покупатель видит «Возврат
  бесплатный»; модератор может поменять с объяснением.
- **Старое приложение** не знает `nofit`: у него причина «неизвестна», и оно спросит её заново. Поэтому: стоит `nofit`
  с гарантией — другую причину через `clocal_return_reason` не принимать (`{ "ok": false, "error": "reason_set" }` с
  готовым текстом); менять — только модератор.

### 8.4. Сроки, доказательства, лимиты

- Окно — до «Подтвердить получение» (`confirm_hours`, обычно 72 ч): хватает поставить планку или SSD. После
  подтверждения — обычная гарантия продавца и споры.
- Доказательства — тем же путём `upload_evidence`: фото маркировки своей вещи (наклейка ноутбука, «Диспетчер задач →
  Память», наклейка шин в проёме двери, «Настройки → Об устройстве») и полученного.
- Вещь — в комплекте, без повреждений сверх попытки установки.
- Лимит — 2 возврата по гарантии на покупателя за 90 дней; дальше — обычные правила (`why: "limit"` при создании).
- Потолок расходов Kliko на межгород — решение владельца (§19). До решения гарантия действует для встречи и доставки
  по городу; у межгорода — `on: false`, `why: "intercity"`.

### 8.5. Каталог учится на ошибках

Каждый `nofit` с итогом `platform` — в список админки «Ошибки «Подходит»» (семья, правило, значения объявления и
`need`; без имён, сделок и сумм) → правка правила каталога и смена `v` (как «Не узнали», `SERVER_STANDARDS.md` §2.6).

## 9. «Подойдёт?» — вопрос продавцу (Авито)

### 9.1. Сообщение `fit_ask`

Кнопка на странице объявления, когда уровень «Проверьте», «Неизвестно» или стандарта у объявления нет: «Спросить
продавца: подойдёт?». Перед отправкой — лист с ровно тем, что уйдёт; любую строку можно убрать. Вещи «Моих детей» и
тело не предлагаются вовсе.

```json
POST /chat.php?action=send
{ "pid": "a1b2c3", "text": "Здравствуйте! Подойдёт к: ноутбук · DDR4 SO-DIMM · до 32 ГБ?",
  "fit_ask": { "kind": "std", "need": "ram_module.gen:DDR4;ram_module.form:SO-DIMM;ram_module.max_gb:32",
               "line": "DDR4 SO-DIMM · до 32 ГБ", "fam": ["ram_module"] } }
```

- `text` — обычное сообщение: старые сборки и сайт видят его как есть. `fit_ask` — структура для ответа.
- В `widget_data`, `poll`, `history` — сообщение `kind: "fit_ask"` с `fit_ask: { …, "answer": null }`.

### 9.2. Ответ Kliko AI — только расчётом

- У объявления есть поля этой семьи и есть правило — ассистент отвечает сам: `role: "ai"`, `kind: "fit_auto"`,
  `fit_auto: { "level": "ok", "part": null, "text": false }` и текст по шаблону: «По стандарту объявления: DDR4 SO-DIMM
  8 ГБ — подходит к DDR4 SO-DIMM. Проверили по стандарту, а не по экземпляру». **Уровень — из правила, модель его не
  придумывает.** Значение из текста — «По описанию продавца — продавец уточнит».
- Вопрос всё равно уходит продавцу (эскалация, как сейчас) — он может подтвердить.

### 9.3. Ответ продавца

Под вопросом у продавца — «Подходит» · «Не подходит» · «Уточню» и «Добавить параметры в объявление» (открывает блок
«Параметры» правки с `need` как предложением — продавец подтверждает каждое, `std_src: ""`; следующие покупатели сразу
увидят «Подходит»).

```
POST /chat.php?action=fit_answer { "msg_id": "m_812", "answer": "yes" } → { "ok": true }
```

- Без `csrf`, как `send`. `answer`: `yes` · `no` · `unsure`; в сообщении — `fit_ask.answer`, `answered_at`; покупателю —
  обычный push чата.
- `yes` — слово продавца в переписке: сделка по этому объявлению из этого чата получает `fit_claim.by: "seller_chat"`,
  `msg_id` (§8.2–8.3).

### 9.4. Правила

- Не чаще одного `fit_ask` в чате за 10 минут и 20 в день на покупателя; `line` ≤ 200 знаков, только значения
  стандартов, без имён вещей «Моего».
- Это сообщение чата по нажатию человека — как любое другое (чат в `PrivacyInfo.xcprivacy` объявлен «Прочим
  содержимым», связанным с человеком; нового не нужно).
- Ответ ассистента без правила — обычный, без `fit_auto`.

| Ключ | ru | kk | en | ar |
|---|---|---|---|---|
| `fa_btn` | Спросить продавца: подойдёт? | Сатушыдан сұрау: сәйкес пе? | Ask the seller: will it fit? | اسأل البائع: هل يناسب؟ |
| `fa_text` | Здравствуйте! Подойдёт к: {line}? | Сәлеметсіз бе! Мынаған сәйкес пе: {line}? | Hi! Will it fit: {line}? | مرحبًا! هل يناسب: {line}؟ |
| `fa_yes` · `fa_no` · `fa_unsure` | Подходит · Не подходит · Уточню | Сәйкес · Сәйкес емес · Нақтылаймын | Fits · Doesn't fit · I'll check | مناسب · غير مناسب · سأتحقق |
| `fa_add` | Добавить параметры в объявление | Параметрлерді хабарландыруға қосу | Add the specs to the listing | أضِف المواصفات إلى الإعلان |

**Готово, когда:** `send` с `fit_ask` даёт сообщение `kind: "fit_ask"`; у объявления со `std` — ответ `fit_auto` с
уровнем правила; `fit_answer` меняет `answer`. **Проба:** §16, «§9».

## 10. Машина по VIN или госномеру (Kaspi, Авито)

### 10.1. VIN или номер кузова

```
POST /api/autofit.php?action=vin
Content-Type: application/json

{ "vin": "JTNB11HK403456789", "lang": "ru" }
→ { "ok": true, "src": "wmi+catalog", "make": "Toyota", "model": "Camry", "year": 2018, "gen": "XV70",
    "body": "sedan", "engine": "2.5", "drive": "fwd", "pcd": "5x114.3", "dia": 60.1, "…": "остальные поля action=car" }
```

- `vin` — 17 знаков без I, O, Q; или `frame` — номер кузова праворульных японских машин («GX110-6012345»), их в
  Казахстане много.
- Ответ — те же поля и ошибки, что у `action=car` (`SERVER_AUTOFIT.md` §1), плюс `src`, `body`, `engine`, `drive`;
  `bad_vin` — формат не тот; `ambiguous` — с `cands: [{ "make", "model", "years" }]`, приложение даст выбрать.
- Что можно без партнёров: производитель — по первым трём знакам (WMI, ISO 3780); год — по 10-му знаку (ISO 3779,
  цикл 30 лет — неоднозначен без модели); модель — таблицы производителей и каталогов запчастей; машины рынка США —
  бесплатный NHTSA vPIC; номер кузова — по коду модели до дефиса.
- **Без кук, только POST** (не в журнал доступа), **не хранить, не писать в журналы и аналитику**, не связывать с
  человеком — как `fit_*` (`SERVER_MY_THINGS.md` §10.2). Лимит — 20 запросов в час с адреса.

На телефоне VIN читает камера (лобовое стекло, стойка двери, СРТС): остаётся только строка VIN; ФИО, ИИН и адрес из
СРТС отбрасываются, кадры не сохраняются. В «Моём» — найденная машина (марка, модель, год); сам VIN — только если
человек выберет «Сохранить VIN», и только на телефоне.

### 10.2. Госномер — только через партнёра

```
POST /api/autofit.php?action=plate   { "plate": "123ABC02", "lang": "ru" }
→ { "ok": true, "src": "partner", "make": "…", "model": "…", "year": 2018, "…": "как vin, без VIN и без владельца" }
```

- Госномер связан с владельцем в государственных базах — это персональные данные (Закон РК «О персональных данных и их
  защите»). Только через партнёра с договором: запрос и ответ не хранит и ни для чего больше не использует. Нет такого
  партнёра — не включать.
- Тот же режим: POST, не хранить, не в журналы, лимит. В ответе — ни VIN, ни данных владельца.
- Если партнёр хранит запросы — это «сбор данных» по Apple: сказать владельцу **до** `circle.plate` (решение и анкета —
  его, §19).

**Готово, когда:** VIN тестовой машины даёт марку, модель и год (или `ambiguous`), кривой — `bad_vin`; в журналах VIN
нет. **Проба:** §16, «§10».

### 11.3. «Подошло?» после покупки → `brand_fit`

### 11.4. Дети: `fit_kids` — только если владелец разрешит

`SERVER_STANDARDS.md` §10.4 оставил это решением владельца. Если «да» — формат готов; до тех пор
`rules.fit_filters.kids: false`, и приложение не шлёт, пока родитель сам не включит в «Моих детях» «Искать по всему
сайту».

```json
POST /api/listings.php?per=24&sort=new
{ "fit_kids": { "std": "child_seat.class:I;child_seat.isofix:1", "size": "kids_height:EU:104|shoes_kids:EU:28" } }
```

- `std` — грамматика `fit_std` (`SERVER_STANDARDS.md` §4.3), группы через `|`; `size` — трёхчастная форма
  `SERVER_MY_THINGS.md` §3.5, только детские таблицы `SERVER_SIZES.md` (`kids_height`, `shoes_kids`). Между частями —
  ИЛИ, как у `fit_*`; ответ — `fit_applied: ["kids"]`, `fit_match.kids`.
- Только **выведенные классы**: группа кресла (`0+`, `I`, `II`, `III`, `i40-87`, `i76-105`, `i100-150`) и ISOFIX машины;
  ряд `kids_height` таблицы детской одежды; размер детской обуви. Никогда — возраст, вес, точный рост, имя, дата
  рождения. `toy_age`, `ball_size`, `brick_system`, `isbn` не шлются (выдают возраст). **Честно:** ряд `kids_height` и
  размер обуви тоже примерно выдают возраст (104 — «3–4 года» по таблице `SERVER_SIZES.md`), поэтому весь `fit_kids` —
  только решением владельца и включением родителем, а не по умолчанию.
- Гарантии — как у `fit_*`: только POST, не хранить, не в журналы, не связывать, `private, no-store`. Не в подписки, не
  в пакет цен, не в `fit_claim`, не в `fit_ask`.
- Кресла: `ok` — только по полям продавца (`safety`), и только если у объявления есть `made` и `no_crash`; иначе
  `check` (`SERVER_STANDARDS.md` §9).
- Включение меняет и `SERVER_MY_THINGS.md` §3.5, §10.5 («детских размеров … не шлём») — правкой в той же пачке.

## 13. Замеры приложения: `api/app_perf.php` и `feed_scroll`

Код — `Sources/Native/System/PerfTelemetry.swift` (пачка и отправка) и `ScrollHitches.swift` (замер листания).
Владелец 16.10.2026: «при листании витрины может подвисать» — новый вид замера `feed_scroll` уже в приложении; сервер
должен его принять.

### 13.1. Пачка

`POST /api/app_perf.php`, JSON, **без кук и `csrf`** — адрес у вас уже есть (правка 104, 06.10: `{ok, n}`, 256 КБ, 30
пачек в час с адреса, 90 дней). Уходит при уходе приложения в фон (не чаще раза в час после удачной отправки) и при
возврате в приложение или запуске, если с удачной отправки прошли сутки. В пачке до 200 замеров (десятки КБ); очередь
на телефоне — до 400; одного вида — до 60 в сутки.

```json
{ "v": 1, "iid": "3f6c2a1e-8b1d-4e7a-9c55-0d2f4b6a1e90", "model": "iPhone15,2", "mem": 6, "ios": "18.6.2",
  "app": "1.13", "build": "412",
  "ev": [ { "k": "feed_scroll", "ms": 58,
            "n": { "frames": 812, "hitches": 4, "lost": 0.017, "lost_ms": 141, "dur_ms": 8130, "hz": 120 },
            "s": { "where": "home" },
            "net": "wifi", "lite": "", "city": "Алматы", "t": 1792137600 } ] }
```

| Поле | Что |
|---|---|
| `v` | версия формата, сейчас 1 |
| `iid` | случайный номер установки — **только для замеров**, не связан с аккаунтом, телефоном и рекламой |
| `model`, `mem`, `ios`, `app`, `build` | модель (`utsname.machine`), память, ГБ, версия iOS, версия и сборка приложения |
| `ev[].k` | вид замера (§13.2) |
| `ev[].ms` | главное значение, мс (может не быть) |
| `ev[].n`, `ev[].s` | прочие числа и строки (могут не быть) |
| `ev[].net` | сеть: `wifi`, `cell-5g` / `-4g` / `-3g` / `-2g`, `wired`, `other`, `none`, `unknown`; хвосты `+exp` (дорогая, режим модема), `+low` (экономия данных); `-` у MetricKit |
| `ev[].lite` | лёгкий режим и почему: `""` или через запятую `hw`, `lowpower`, `thermal` |
| `ev[].city` | город, **выбранный в шапке** (название, `r:<регион>` или `all`), не координаты |
| `ev[].t` | Unix-время с точностью до минуты |

| `k` | `ms` | `n` | `s` |
|---|---|---|---|
| `cold_feed` | от старта процесса до первой карточки ленты | — | `src`: `disk` / `net`; `pre`: `1` / `0` (предзапуск iOS) |

### 13.3. `feed_scroll`

Одно событие — одно листание ленты или витрины главной: от касания до остановки инерции, не дольше 30 с и не меньше 10
кадров. Период кадра берётся у `CADisplayLink` самого телефона (8,3 мс на 120 Гц, 16,7 мс на 60 Гц), поэтому кадр
120 Гц не считается долгим по мерке 60 Гц. Ушли из приложения посреди листания — события нет.

| Поле | Что | Пределы |
|---|---|---|
| `ms` | худший кадр: самый долгий шаг между кадрами, мс | 0…60 000 |
| `n.frames` | кадров за листание | 10…10 000 |
| `n.hitches` | подвисаний: кадр дольше 1,5 ожидаемого периода | 0…`frames` |
| `n.lost` | доля потерянного времени, 0…1, три знака | 0…1 |
| `n.lost_ms` | потеряно, мс: всё сверх периода у долгих кадров | ≤ `dur_ms` |
| `n.dur_ms` | длилось, мс | ≤ 60 000 (обычно ≤ 30 000, последний кадр может перешагнуть) |
| `n.hz` | частота экрана в замере: 60, 120 (ProMotion), бывает 30 и 80 | 1…240 |
| `s.where` | `home` — витрина главной, `feed` — лента раздела или поиска; другие — принять как есть | ≤ 16 знаков |

Модели телефона в событии нет: она у пачки (`model`, «iPhone15,2»), сводке по моделям брать её оттуда
(`ЗамерыСкорости.листание` в `PerfTelemetry.swift` кладёт в `s` только `where`).

### 13.4. Приём — не терять пачки

- **Приложение выбрасывает пачку на любой 4xx, кроме 429** (`PerfTelemetry.swift`: «тело кривое или эндпоинта нет — не
  копим её вечно»). Поэтому незнакомый `k`, незнакомые ключи в `n` и `s`, значение вне пределов — **не повод для 4xx**:
  такое событие пропустить (или сохранить как есть), остальные принять → `200 { "ok": true, "n": 199, "skipped": 1 }`
  (`n` — как сейчас, `skipped` — новое). Если сейчас `k` сверяется по списку — **добавьте `feed_scroll`**, а лучше
  принимайте любой.
- 4xx — только как сейчас: не JSON (400 `bad_json`), больше вашего предела 256 КБ (413 `size`), не POST (405).
- Перегрузка — `429`: приложение оставит пачку и повторит при следующем уходе в фон или открытии (`Retry-After` не
  читает).
- 5xx — пачка останется на телефоне до следующей отправки.
- Куки, если пришли, не читать. Ответ — быстро: запись в таблицу или очередь, без расчётов в запросе.

### 13.5. Хранение и сводка

- Сырые события — как у вас сейчас (90 дней, `data/app_perf/*.jsonl`); сводка — год: день × `k` × `model` (пачки) ×
  `where` × `hz` × сборка × `lite` × `net` — число, P50 и P90 `ms`; у `feed_scroll` ещё Σ`frames`, Σ`hitches`,
  Σ`lost_ms`, Σ`dur_ms`.
- Показатели листания: доля листаний с подвисанием; подвисаний на 1 000 кадров; **время рывков = Σ`lost_ms` ÷
  (Σ`dur_ms` ÷ 1000), мс на секунду листания** — та же единица, что `hitch` у `mx_day` (MetricKit
  `scrollHitchTimeRatio`), их можно сравнивать. Ориентир Apple: меньше 5 мс/с — хорошо, 5–10 — заметно, больше 10 —
  плохо.
- Страница админки «Скорость»: по моделям (iPhone XR … 17 Pro), по `where`, по сборкам; пять худших моделей; изменение
  от сборки к сборке.
- Уникальные устройства — по хэшу `iid` с солью сервера; с аккаунтами не сводить никогда.

### 13.6. Приватность

В `PrivacyInfo.xcprivacy` объявлены «Данные о производительности» и «Данные о сбоях» — **не связанные с
пользователем**. Так и держать: без кук, IP рядом с событиями не хранить (остаётся только журнал хостинга), `iid` —
только для замеров, `city` — выбранный город, не координаты; не для рекламы и рекомендаций.

### 13.7. Включение

Админка «iOS-приложение» → ключ `perf_telemetry` (`Native/System/RemoteSettings.swift`): в сборке выключено
(`Config.телеметрияСкоростиВСборке = false`) — включить, когда адрес принимает пачки по §13.4. Выключить — тем же
ключом: замеры перестают копиться и уходить.

**Готово, когда:** пачка с `feed_scroll` → 200 и событие в таблице; пачка с одним кривым и одним незнакомым событием
→ 200, `skipped` ≥ 1, хорошее сохранено; не JSON → 400; сводка по моделям видна в админке. **Проба:** §16, «§13».

## 14. Модерация

  сервер — подделать её подачей нельзя.

- `nofit`: модератор решает, кто прав, по §8.3; ошибки правил — в список каталога (§8.5).
- `color`, `size_fit`, `knockdown`, `pass_cm` — заявление продавца; заведомо ложное — как неверное описание.
- Сборки: бронь чужих объявлений без оплаты — одна неоплаченная сборка, срок брони как у сделки; повторяется — как
  злоупотребление сделками сейчас.
- `brand_fit` — только при пороге; один голос на покупателя и бренд.

## 19. Вопросы

### 19.1. К ultra-site

1. `product_img` в сделке — хранится на момент создания или берётся из живого объявления? От этого — нужно ли `img` в
   снимке (§2.2).
2. Может ли итог смениться после `sold` (возврат по гарантии продавца)? Бывает ли частичный возврат денег по спору —
   тогда `refund_part` (§2.2)?
3. Когда гарант снимается с паузы (`MK_ESCROW_PAUSED`)? От этого зависят сборки, гарантия и галочка «Моё».
4. Сборка: одна оплата картой на несколько сделок — умеет ли шлюз частичный возврат? Если нет — возврат части на
   кошелёк (§7.6).
5. Один курьер на несколько сделок одного продавца (`ship_group`, §7.7) — можно?
6. Push по сохранённым поискам уже идёт (ваш `APP_CHANGES.md` 29.09: тип `sub`, по одному на одобренное объявление,
   `src=ss`) — вопрос 4 `SERVER_STANDARDS.md` §13 этим закрыт. Подтвердите, что подписки `kind: fit` (и со `std`) в эту
   мгновенную рассылку и в прежний `list` не попадут (§6.3–6.4), и есть ли у неё сейчас дневной предел на человека.
7. Чат: может ли ассистент отвечать расчётом (`fit_auto`), а не текстом модели? Отдают ли `poll` и `history` свои
   `kind` сообщений (§9)?
8. VIN: какие таблицы у вас есть или можно купить? Госномер: есть ли партнёр и что он хранит (§10)?
9. `app_perf.php` (есть с 06.10, правка 104): сверяет ли `k` по списку — тогда `feed_scroll` получит 4xx и пачки
   потеряются (§13.4)? Где будет сводка листания — в блоке «Падения и зависания» или своя страница «Скорость»? Предел «30
   пачек в час с адреса»: у мобильных операторов за одним адресом тысячи телефонов — 429 пачки не теряет, но задерживает;
   поднять предел или считать по хэшу `iid`?
10. Есть ли у формы сайта поле цвета у одежды (в `E_SPECS` или своё)? Если да — сведём с палитрой §11.2.
11. «Продать своё»: удобнее отдавать черновик (`relist_draft`) или сайту проще собирать его в JS из `deal` — тогда
    достаточно `relist_from` (§4)?

### 19.2. Решения владельца

| Вопрос | Предлагаем по умолчанию |
|---|---|
| Гарантия «Подходит»: кто платит при ошибке правила | Kliko (`platform`); лимит 2 возврата за 90 дней; межгород — после того, как вы назовёте потолок; галочка гарантии по умолчанию выключена, одно касание включить |
| Размеры одежды в «Новинках» (`saved_fit_size`) | да, только взрослые таблицы, после первой волны «Новинок» |

| Госномер через партнёра | только с партнёром, который не хранит запросы; до того — только VIN |
| «Сколько стоит всё моё» | не показывать по умолчанию (`docs/STANDARDS.md` §13) |
| Сбор за сборку | сумма сборов сделок, как сейчас |
| «История поиска» в анкете App Privacy | добавить до «Новинок» — и за нынешние сохранённые поиски |
