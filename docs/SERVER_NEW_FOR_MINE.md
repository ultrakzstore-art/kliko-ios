# «Новинки для моего»: магазин обновился — человек узнал сам. Что нужно от сервера

Документ для разработчика сайта kliko.kz (ultra-site), 17.10.2026, первая редакция. Продолжает
`docs/SERVER_STANDARDS.md` (+ `SERVER_STANDARDS_catalog.json`), `docs/SERVER_MY_THINGS.md`, `docs/SERVER_SIZES.md`,
`docs/SERVER_DIMENSIONS.md`, `docs/SERVER_SIZE_TEMPLATES.md`, `docs/SERVER_CIRCLE.md` и ни одному из них не противоречит:
**поля и параметры только добавляются**, имена — из этих договоров, что уже есть там — здесь только ссылкой на §.
Два исключения: §3 предлагает **заменить** подписки «Новинок» в аккаунте подпиской без входа (вопрос владельцу В1);
§1.2 п. 1 уточняет `SERVER_STANDARDS.md` §3.2 («шины `std` не шлют — пришли, игнорировать»): две семьи индексов шин
теперь принимаются в `std`.

Слова владельца, 17.10.2026:

> «Как это работает, когда у шопов обновление? Новая коллекция… так же шины и всё остальное» → «да, пиши задание
> ultra-site» → «и делай в 83, и что ещё можно упростить?»

## Зачем

Магазин залил новую партию — зимние шины, коллекцию «осень-зима», матрасы 160×200. Человек, которому это подходит, видит
это сам: в «Для вас» с меткой «3 новых» и одним push-ом в день. Сервер знает товар, телефон знает «Моё»; встречаются они
только **значениями стандартов** — без имени, без аккаунта, без «Моего» целиком.

```
 МАГАЗИН                        СЕРВЕР ultra-site                          ТЕЛЕФОН («Моё» живёт только здесь)
 таблица · фид ──§1──► объявления со стандартами ◄──§2── POST: только значения («205/55R16», «E14»)
 «Осень-зима 2026» §5   (std · parts · размеры)  ──────► подходящие + уровень + деталь
                              │                                              │
                              ├─§3─ подписка без входа: sid + токен + значения ── push ≤ 1/день ──► «Для вас · 3 новых»
                              ├─§4─ сезон: порядок полок (то же встроено в приложение)
                              ├─§6─ магазину: «Астана · шины 205/55 R16 · 40+ ждут» (меньше 20 — не показываем)
                              ├─§7─ «Реклама»: кандидаты по разделу, сверка — на телефоне
                              └─§8─ неверный стандарт: жалоба → модератор → ниже в выдаче
```

## 0. Общее

- Поля и параметры **только добавляются**. Старые сборки их не шлют и не читают, старый сервер молча игнорирует. Ни
  один прежний ответ не меняется.
- Адреса: `api/listings.php`, `api/for_mine.php` — от корня, JSON, **без куков и `csrf`**; действия магазина —
  `/kz/<язык>/cabinet.php` с куками и `csrf`, как сейчас у импорта (`Import/ImportAPI.swift`).
- Языки — `ru`, `kk`, `en`, `ar`. Тексты `error` и push — на языке запроса или подписки.
- **«Не поддерживается»** (приложение до перезапуска не спрашивает и работает по-старому): HTTP 404, 405, 410, 501,
  любой 3xx, не JSON, `{"ok": false, "error": "unsupported"}` или `"off"` (ключ админки выключен). **Временный сбой**
  (повтор при следующем открытии): обрыв, таймаут 15 с, 5xx, 429.
- Всё новое — за ключами админки «iOS-приложение» (§11), **по умолчанию выключено**.

### 1.2. Шины — три уточнения к прежним договорам

1. **Индексы — в `std`.** `SERVER_STANDARDS.md` §3.2 говорит «шины и диски `std` не шлют». Это про размер, диск и сезон —
   они в `parts`. Семей `tyre_load_index` и `tyre_speed_index` в `parts` нет: принимать их в `std` (раздел
   `tires-wheels` — в их `cats`). Если в мастере уже есть такие поля — скажите имена (У2), выдадим их в `std` при
   выдаче, как `tyre_size`.
2. **`parts.dot`** — неделя и год выпуска, 4 цифры как на боковине («DOT … 3525» — 35-я неделя 2025). Неделя 01…53, год
   не в будущем. Нужен: срез цены `dot_age` (≤ 3 · 3–6 · > 6 лет, уже в каталоге у `tyre_size.price.slices`) и строка у
   покупателя «Год выпуска: 2025». Эталон разбора есть в каталоге (`tests.ocr`: `_dot {week, year}`), но камера
   приложения DOT пока **выбрасывает** (`TryOn/WheelScanParse.swift`) — чтение DOT камерой не в 83.
   Магазин написал только год («2019») — тоже годится: для возраста важен год, а он у «2019» и «3519» один. Старше
   6 лет — сохранить и предупредить в отчёте (§1.5), не отказывать.
3. **Сезон** — значения каталога `tyre_season`; «шипы» — это `winter_studded`, отдельного поля нет. Синонимы — каталог
   (`aliases`, `aliases_market`: «шиповка», «липучка», «шипті»).

### 1.3. Таблица (CSV, XLSX): карта столбцов на стандарты

Путь тот же, что сейчас: файл → `ai_import_extract` (текст) → разбор шапки (`_tblToItems`, синонимы `_TBL_SYN`) →
строки на проверку → `ai_import_publish` → черновики. Добавляется **цель столбца — поле §1.1**:

```
Артикул;Название;Цена;Бренд;Ширина;Профиль;Диаметр;Сезон;Нагрузка;Скорость;DOT;Кол-во;Остаток;Фото
MX-2055516;Michelin X-Ice North 4 205/55 R16 94T;240000;Michelin;205;55;16;шипы;94;T;3525;4;12;https://…/1.jpg
```

```json
{ "sig": "1a2b3c4d5e6f7a8b", "cols": ["Артикул · MX-2055516", "Название · Michelin X-Ice…", "…"],
  "map": { "ext_id": 0, "title": 1, "price": 2, "brand": 3, "parts.width": 4, "parts.profile": 5, "parts.diameter": 6,
           "parts.season": 7, "std.tyre_load_index.li": 8, "std.tyre_speed_index.speed": 9, "parts.dot": 10,
           "qty": 11, "stock": 12, "images": 13 } }
```

- Карта хранится тем же `import_fmt {sig, map, cols}` (у формата магазина один раз — дальше узнаётся сам по подписи
  `_tblSigOf`). Цели — **любые строки** вида `std.<семья>.<поле>`, `parts.<поле>`, `storage`, `size_sys`, `size_avail`,
  `color`, `collection.name`, `ext_id`, `stock`; незнакомую цель — пропустить.
- Подсказки целей — из каталога, без нового адреса: `title` семьи и поля, `aliases`, `aliases_market`, `keywords`
  (`api/standards.php`, `SERVER_STANDARDS.md` §2.2). Пример: «Индекс нагрузки», «Нагрузка», «LI», «Жүктеме индексі» →
  `std.tyre_load_index.li`.
- Цель **`parse`** — «разобрать как название»: «205/55 R16 94T» одним столбцом раскладывается правилами `ocr` и
  `title_examples` каталога (размер, индексы).
- Значения — нормализация каталога (`SERVER_STANDARDS.md` §2.5: «Е27» → E27, «5х114,3» → 5x114.3, «зима шипы» →
  `winter_studded`).
- Строка в `ai_import_publish` несёт цели **вложенно** (`std`, `parts`, `collection`, как в §12) **или плоско** — ключом
  цели и текстом ячейки (`"std.tyre_load_index.li": "94"`, `"parts.dot": "3525"`); сервер принимает обе формы и
  нормализует одинаково.
- **Приложение:** всё, что вернёт ваш `ai_import` (в том числе `std`, `parts`), уходит в `ai_import_publish` как
  пришло. Свой разбор таблицы (`ТаблицаИмпорта`) знает только базовые поля; карту с чужими целями он не портит
  (`import_fmt` сохраняется с ними, `ImportModel.сменитьРазметку`), а в 83 ячейки незнакомых ему целей кладёт в строку
  плоско, как пришли (§9). Без этого таблица, разобранная в приложении, ушла бы без стандартов.

### 1.4. Фид (YML, JSON)

```
POST /kz/ru/cabinet.php?action=feed_add  { "csrf": "…", "url": "https://shop.kz/kliko.yml", "format": "yml", "every_h": 6,
                                           "sig": "…", "collection": { "name": "Осень-зима 2026", "season": "aw", "year": 2026 } }
                                         → { "ok": true, "id": "f12", "next_at": "2026-10-17T18:00:00+05:00" }
GET  /kz/ru/cabinet.php?action=feed_list → { "ok": true, "feeds": [ { "id": "f12", "url": "…", "format": "yml", "every_h": 6,
                                             "last_at": "…", "last": { "added": 40, "updated": 112, "removed": 3, "warn": 9, "skipped": 1 } } ] }
POST /kz/ru/cabinet.php?action=feed_run  { "csrf": "…", "id": "f12", "check": 1 }  → отчёт §1.5 без изменений
POST /kz/ru/cabinet.php?action=feed_del  { "csrf": "…", "id": "f12" }              → { "ok": true }
```

| Формат | Что куда |
|---|---|
| YML (`<yml_catalog>`) | `<offer id>` → `ext_id`; `<name>`, `<price>`, `<vendor>` → `title`, `price`, `brand`; `<picture>` → `images`; `<categoryId>` → раздел Kliko по карте категорий магазина (один раз в кабинете); `<param name="…">` → цель по тем же подсказкам каталога (§1.3); `<available>false</available>` → снять с публикации |
| JSON | `{ "items": [ { "ext_id", "title", "price", "category", "brand", "qty", "stock", "images", "std", "parts", "storage", "size_sys", "size_avail", "color", "collection" } ] }` — имена §1.1 |
| CSV по ссылке | как таблица §1.3, карта по `sig` |

- Обновление по `ext_id`: изменились цена, `stock`, `size_avail` — правка объявления без повторной модерации;
  изменились название, фото, раздел, `std` — как правка продавца сейчас. Нет в фиде два прогона подряд — снять
  (неактивное), не удалять. Новое — **черновиком** (автопубликация — решение владельца, В6).
- Пределы (предложение): https, ≤ 20 МБ, ≤ 5 000 предложений, ≤ 3 фида на магазин, не чаще раза в 6 ч, таймаут 60 с;
  фото — тем же конвейером, что импорт, одно скачивание на адрес.
- Адрес фида задаёт магазин — сервер качает его сам: только публичные адреса (не `localhost`, не 10.x, 172.16–31.x,
  192.168.x, 169.254.x, не IPv6-локальные — и после редиректа), XML — без внешних сущностей (XXE: `LIBXML_NONET`, без
  `LIBXML_NOENT`).
- `collection` фида — на все его предложения; своё поле предложения главнее.

### 1.5. Проверка и отчёт

`ai_import_publish` и `feed_run` принимают **`check: 1`** — ничего не создают, только отчёт. Без `check` — черновики
и тот же отчёт. **Из-за стандартов строку не отклонять никогда** (`SERVER_STANDARDS.md` §3.2): плохое значение
отбрасывается, строка проходит, в отчёте — предупреждение.

```json
{ "ok": true, "added": 118, "skipped": 1, "warn": 3, "std_rows": 110, "std_share": 0.93,
  "report": [
    { "row": 7,  "col": "Сезон", "field": "parts.season", "code": "std_value", "got": "зима-лето", "kept": false,
      "msg": "Не узнали сезон: летние, зимние шипованные, зимние фрикционные или всесезонные" },
    { "row": 12, "col": "DOT", "field": "parts.dot", "code": "dot_bad", "got": "19", "kept": false,
      "msg": "Нужно 4 цифры — неделя и год, как на шине: 3519 (или год: 2019)" },
    { "row": 30, "col": "Название", "field": "title", "code": "title_empty", "got": "", "kept": false, "msg": "Строка без названия пропущена" } ] }
```

| `code` | Что | Строка | Значение |
|---|---|---|---|
| `title_empty` | нет названия | **пропущена** | — |
| `cat_unknown` | раздел не найден | черновик без раздела, просим выбрать | — |
| `price_bad` | цена не число | черновик без цены | — |
| `dup_ext_id` | артикул повторяется в файле | первая берётся, остальные пропущены | — |
| `std_family` | семья не для этого раздела (`cats` каталога) | проходит | отброшено |
| `std_value` | значение вне ряда, но правдоподобное | проходит | сохранено как `other`, у покупателя «Проверьте» |
| `std_range` | неправдоподобное (DDR9, PCD 9x300) | проходит | отброшено |
| `size_unknown` | размера нет в таблицах `SERVER_SIZES.md` | проходит | отброшено |
| `dot_bad`, `dot_future` | не 4 цифры, неделя > 53, год в будущем | проходит | отброшено |
| `dot_old` | шине больше 6 лет | проходит | сохранено, предупреждение |
| `qty_bad` | не 1…999 | проходит | `qty: 1` |
| `stuffing` | набивка: 20 цоколей, «все VESA», «все сокеты» (§8) | проходит | семья отброшена |

- При `check: 1` — `added: 0`; `skipped`, `warn` и `report` — как будут при загрузке.
- `ext_id` уже есть у этого магазина — **правка** того объявления по правилам фида (§1.4), а не новый черновик; в ответе
  — `updated`. `dup_ext_id` — повтор внутри одного файла (пачки по 50 строк одной загрузки — по `job`, если он пришёл).
- `std_share` — доля строк хоть с одним принятым стандартом: магазину видно, насколько его товар «найдётся сам».
- Тексты `msg` — готовые, на языке запроса, с тем, **как правильно**.

### 1.6. Черновики и публикация

- Черновики — как сейчас (`imp_draft`, «Неактивные»). «Опубликовать все без предупреждений» — одной кнопкой кабинета.
- `batch` в `ai_import_publish` — общее на пачку: `{ "batch": { "collection": { … } } }`; своё поле строки главнее.
- Модерация — как у обычной подачи; при `std_share` < 0,2 у магазина с прошлым ≥ 0,8 — пометка модератору
  (сломалась карта столбцов).

**Готово, когда:** таблица шин с примера даёт черновики с `parts`, `std` индексов, `parts.dot`, `qty: 4`; `check: 1` не
создаёт ничего; плохой DOT — `dot_bad`, строка прошла; карта узнаётся по `sig` во второй раз; фид обновляет цену по
`ext_id` и снимает пропавшее. **Проба:** §12, «§1».

## 2. Подбор на сервере: значения стандартов → подходящие из всей базы

### 2.1. Запрос

Тот же `api/listings.php` и те же `fit_*` (`SERVER_MY_THINGS.md` §3, `SERVER_STANDARDS.md` §4.3), только **без `cat`**
и сразу по всем вещам «Моего» — для «Для вас» один запрос вместо 3–6:

```
POST /api/listings.php?per=48&sort=new&per_g=8&city=Алматы&lang=ru
Content-Type: application/json
(без куков)

{ "fit_std": "bed_size.size:160x200|lamp_base.base:E14|ram_module.gen:DDR4;ram_module.form:SO-DIMM;ram_module.max_gb:32",
  "fit_car": "pcd:5x114.3;dia:60.1;et:35..45;r:16,17;tyre:205/55R16",
  "fit_phone": "iphone-15-pro", "fit_laptop": "15.6",
  "size": "shoes_men:EU:43|clothes_men:INT:M",
  "fit_level": "parts",
  "cats": "tires-wheels,bedding,beds,lighting,ram,phone-cases,mens-shoes,mens-clothing" }
```

| Что | Где | Что значит |
|---|---|---|
| `fit_*`, `size`, `fit_level` | тело | как в договорах; между видами — ИЛИ, группы `fit_std` через `\|` — ИЛИ, номер группы `g` |
| **`cats`** | тело | разделы, где искать (с потомками), до 20. Нет — каждый вид в своей области (`fit_car` — `tires-wheels`, `fit_std` — `cats` семьи). В адрес не кладём: набор разделов собран из «Моего» |
| **`per_g`** | адрес | не больше столько на группу (вещь) на страницу, по умолчанию 8: одна машина не займёт всю страницу |
| `per` ≤ 48, `page`, `sort`, `city`, `lang`, `seed` | адрес | как у ленты |

- **Без куков.** Приложение шлёт этот POST без куков (как сейчас GET «Для вас»); пришли — для отбора не читать, ответ
  не персонализировать. Своё объявление отсекает телефон.
- Значение не разобралось — часть пропускается (не 400). Семьи `fit_std: false` и `"kids_optin"`, `fit_me`, `fit_kids` —
  игнорировать (`SERVER_STANDARDS.md` §10).

### 2.2. Ответ

```json
{ "ok": true, "total": 61, "has_more": true, "fit_applied": ["std", "car", "size"],
  "totals": { "std:0": 9, "std:1": 14, "std:2": 3, "car": 27, "size": 8 },
  "items": [ { "id": "d4e5f6", "category": "lighting", "std": { "lamp_base": { "base": "E27" } },
               "fit_match": { "std": { "g": 1, "level": "adapt", "by": { "lamp_base": "adapt" }, "part": "E14→E27" } } },
             { "id": "a1b2c3", "category": "tires-wheels", "qty": 4,
               "parts": { "kind": "tire", "width": "205", "profile": "55", "diameter": "16", "season": "winter_studded", "dot": "3525" },
               "fit_match": { "car": "ok" } } ] }
```

| Уровень приложения (`УровеньАвтоподбора`) | Сервер | Что |
|---|---|---|
| Подходит | `ok`; у чехлов ещё `universal` (`fit_match.phone`) | совпало по правилу; значение — от продавца (`std_src` из `ok_from` каталога) |
| Нужна деталь | `adapt`; у машины `rings`, `spacers`, `rings+spacers` | деталь всегда названа: `part` |
| Неизвестно | — | не хватает данных в «Моём» — только телефон |
| Проверьте | `check`; `text`, `tight`, `loose` | нет поля, значение из текста, пограничный допуск |
| Не подходит | — | исключено, в ответ не идёт |

- **Причину** собирает телефон из `g`, `by`, `part` и полей объявления («Для вашей Camry · 205/55 R16», «Нужна деталь:
  переходник E14 → E27»). Текста причины сервер не шлёт.
- Уровень на телефоне — **не лучше `fit_match` сервера**: в нём учтено доверие к продавцу (§8.3), которого телефон не
  видит.
- `totals` — честное число подходящих по каждой группе (`std:<g>`, `car`, `phone`, `laptop`, `size`): «Для кровати — 14».
- Отбор сервера грубый, **без ложных «нет»** (`SERVER_STANDARDS.md` §4.3): телефон всё равно досчитывает по полному
  «Моему».
- ТОП (`slot: "top"`) — только подходящий и с обычной пометкой, как договорено; в «Для вас» телефон ТОП-вставки не берёт.

### 2.3. Отказы

| Ответ | Приложение |
|---|---|
| нет `fit_applied` (старый сервер) | считает «не применено»: прежний путь — GET по разделам и сверка на телефоне |
| `400 bad_json`, `413` (тело > 8 КБ) | прежний путь до перезапуска |
| `429`, 5xx, таймаут 15 с | показывает то, что в памяти; повтор не раньше чем через минуту |
| `{"ok": false, "error": "off"}` | ключ `std_server_fit` выключен — прежний путь |

### 2.4. Кеш и журналы

- Кешировать можно **только публичное**: пул свежих объявлений раздела × город на 1–5 минут, разобранные `std`
  объявлений. Ключ кеша **не строить из тела**, тело не хранить даже хэшем.
- Ответ — `Cache-Control: private, no-store`. Память на телефоне — 15 минут (уже так).
- Тело — не в журналы доступа и ошибок, не в отладку (`php://input` в `error_log` не писать), не в БД, не в аналитику
  (можно счётчик «запросов с `fit_*`» без значений), не в рекламу и рекомендации (`SERVER_MY_THINGS.md` §10.2).
- Пределы: тело ≤ 8 КБ, групп ≤ 12, `per` ≤ 48, `page` ≤ 10; частота — 60 в минуту с адреса (429).

**Готово, когда:** POST без `cat` с тремя видами даёт `fit_applied`, `totals`, `g`; при `fit_level: parts` нет
`check`; из текста — не лучше `check`; с куками и без — одни и те же номера; тела нет в журналах. **Проба:** §12, «§2».

## 3. «Новинки для моего»: подписка с телефона, без входа

### 3.1. Как устроено

- **Одна запись на телефон**, без аккаунта: случайный `sid` (его знает только телефон), токен push, те же значения,
  что тело §2.1, город, язык, часы тишины. Гостю тоже.
- Сервер раз в 1–3 часа сверяет **новые одобренные** объявления с подписками тем же отбором, что §2, и раз в день
  присылает **одно** сообщение на все находки.
- Создаётся **только** по явному «Сообщать о новом» в приложении (окно разрешения push — в этот момент). Никогда сама
  из «Моего».
- **Без куков и сессии.** Приложение шлёт `api/for_mine.php` без куков; пришли — не читать, `session_start` не звать,
  запрос ни с кем не связывать. `sid` — только в теле, никогда в адресе.
- Заменяет шаг Б `SERVER_STANDARDS.md` §7.2 и `kind: "fit"` `SERVER_CIRCLE.md` §6 (В1): их флаги `rules.std.subs`,
  `circle.saved_fit`, `circle.saved_fit_size` не включать. Обычные сохранённые поиски `subs.php` — как есть.

### 3.2. `POST /api/for_mine.php?action=sub_put` — создать или заменить

```json
{ "sid": "9f2c6a0e4b7d4e1c8a3f5b6d7e8f9a0b",
  "token": "5e1c…(64–200 hex)", "env": "prod",
  "lang": "ru", "tz": "Asia/Almaty", "city": "Алматы",
  "want": { "fit_std": "bed_size.size:160x200|lamp_base.base:E14",
            "fit_car": "pcd:5x114.3;dia:60.1;et:35..45;r:16,17;tyre:205/55R16",
            "size": "shoes_men:EU:43|clothes_men:INT:M",
            "fit_level": "parts", "cats": "tires-wheels,bedding,lighting,mens-shoes,mens-clothing" },
  "daily": 1, "quiet": [22, 9] }
→ { "ok": true, "exp": "2027-01-15", "daily": 1, "quiet": [22, 9], "dropped": [] }
```

| Поле | Что |
|---|---|
| `sid` | 32 hex (128 бит) из системного случайного (`SecRandomCopyBytes`), **не** из `identifierForVendor`, номера аккаунта или токена; создаёт телефон один раз, после «Удалить всё «Моё»» — новый; **это ключ** — по нему меняют и удаляют. Сервер хранит только `sha256(sid)` |
| `token` | токен APNs, 64–200 hex; сменился — тот же `sid`, новый `token`. Тот же `token` пришёл под другим `sid` — прежнюю запись удалить: один телефон — одна подписка, без двойных push |
| `env` | `prod` (App Store и TestFlight) · `sandbox` (отладка) |
| `lang`, `tz` | язык push; пояс тишины (Казахстан с 01.03.2024 — один пояс UTC+5) |
| `city` | город для отбора; нет — весь Казахстан |
| `want` | **ровно тело §2.1** без адресных параметров: `fit_std` (группы `\|`, ≤ 12), `fit_car`, `fit_phone`, `fit_laptop`, `size` (взрослые таблицы), `fit_level` (`ok` · `parts`; пришло `check` или ничего — ставить `parts`), `cats` |
| `daily` | push в сутки, 1 по умолчанию; больше `fit_subs_daily` (§11) — обрезать |
| `quiet` | часы тишины `[с, до]`; принимать только **шире** 22–9 |
| ответ `exp` | до какого дня живёт без продления (90 дней от последнего `sub_put`) |
| ответ `dropped` | что не принято: `["fit_me", "fit_std:3"]` — приложение покажет честно |

- Идемпотентно по `sid`: запись заменяется целиком. Пустой `want` (`{}`) — запись удаляется, `ok`. В `want` что-то
  есть, но ничего принимаемого — `fit_empty`, прежняя запись **не меняется**.
- **Без имён и подписей**: ни `label`, ни названий вещей («Camry», «спальня») телефон не шлёт.
- Никогда: `fit_me`, `fit_kids`, семьи `fit_std: false` и `"kids_optin"`; вещи «Моих детей» телефон не кладёт вовсе.

### 3.3. `sub_get`, `sub_del`

```
POST /api/for_mine.php?action=sub_get  { "sid": "…" } → { "ok": true, "want": { … }, "city": "Алматы", "lang": "ru",
                                                           "daily": 1, "quiet": [22, 9], "created": "2026-10-17",
                                                           "exp": "2027-01-15", "last_sent": "2026-10-18" }
POST /api/for_mine.php?action=sub_del  { "sid": "…" } → { "ok": true }        (нет такой — тоже ok)
```

- `sub_get` — человек видит ровно то, что хранится (право на доступ, Закон РК «О персональных данных и их защите»).
- `sub_del` — **сразу**: запись, список виденного, ключи `fit_subs_keys`, очередь (в резервных копиях базы — не дольше
  их обычного срока). Телефон зовёт при выключении, «Удалить всё «Моё»» и выходе из аккаунта (выход стирает «Моё» с
  телефона).

### 3.4. Отбор и отправка

- В находки — объявления, **одобренные** после прошлой проверки этой подписки: не поднятые старые (поднятие — не
  новинка), не переопубликованные в течение 30 дней. Город — как у подписки.
- Уровень — по `fit_level`: `ok`; при `parts` — ещё `adapt` (у машины `rings`, `spacers`). **Из текста и примерного**
  (`std_src` `text`, `tpl`; `compat_src: "text"`) — нет: это «Проверьте». Продавцы со сниженным доверием (§8.3) — нет.
- Одно объявление в подписке — один раз за её жизнь (`fit_subs_seen`, 500 номеров, 90 дней). Своё объявление сервер
  отличить не может (аккаунта нет) — телефон его не покажет.
- Отправка — окно 10:00–21:00 по `tz`, сжатое тишиной подписки (`quiet` [21, 10] — 10:00–21:00, [20, 11] —
  11:00–20:00), время внутри окна — по хэшу подписки (разнос нагрузки); не больше `daily` в сутки; в тишину — никогда;
  накопленное ночью уходит утром одним сообщением. Нет находок — нет push. Никогда «загляните, у нас новое».

### 3.5. Push

```json
{ "aps": { "alert": { "title": "Новинки для моего",
                      "body": "3 новых: шины 205/55 R16 от 240 000 ₸ за 4 шт · лампы E14 от 900 ₸" },
           "thread-id": "fit_new", "category": "FIT_NEW", "sound": "default" },
  "type": "fit_new", "url": "/cabinet.php?go=foryou&new=1",
  "ids": ["a1b2c3", "d4e5f6", "c7d8e9"], "g": ["car", "std:1"], "n": 3 }
```

- Текст собирает **сервер из найденных объявлений**: подпись — по `line` семьи каталога (как строка «Параметры»,
  `SERVER_STANDARDS.md` §3.6), у шин и дисков — по `parts`, у одежды — раздел и размер; «от» — самая низкая цена
  находок с единицей (`per`: «за 4 шт»). До двух групп в тексте, дальше — «и ещё N».
- `ids` — до 20 номеров: телефон ставит их первыми **среди загруженного обычным путём** «Для вас» и отдельно по ним
  не догружает — набор номеров одного push — отпечаток подписки, ему нечего делать в адресе запроса рядом с куками;
  `g` — какие группы `want` нашлись (`std:<g>`, `car`, `phone`, `laptop`, `size`); `n` — всего находок.
- Заголовки APNs: `apns-push-type: alert`, `apns-priority: 5` (сводка, не срочное), `apns-collapse-id: fit_new`,
  `apns-expiration` — конец сегодняшнего окна.
- `url` — экран «Для вас» (в 83 — `go=foryou`, §9). Старые сборки такой push не получат: подписку создаёт только 83.
  Сайту `?go=foryou` можно понимать как кабинет.
- Категория `FIT_NEW` — у приложения действие «Не присылать для этого»: телефон убирает группы `g` из `want` и шлёт
  `sub_put`. Серверу ничего.
- Push — только на то, на что человек подписался, с выключением в приложении (App Review 4.5.4).

| Ключ | ru | kk | en | ar |
|---|---|---|---|---|
| `fn_title` | Новинки для моего | Менікі үшін жаңалар | New for My Things | جديد لأشيائي |
| `fn_body` | {n} новых: {a} · {b} | {n} жаңа: {a} · {b} | {n} new: {a} · {b} | {n} جديد: {a} · {b} |
| `fn_from` | {label} от {price} | {label} — {price} бастап | {label} from {price} | {label} من {price} |
| `fn_set4` | за 4 шт | 4 дана үшін | for a set of 4 | لطقم من 4 |
| `fn_more` | и ещё {k} | және тағы {k} | and {k} more | و{k} أخرى |
| `fn_coll` | Новая коллекция «{name}» в вашем размере: {n} | Жаңа «{name}» коллекциясы сіздің өлшеміңізде: {n} | New “{name}” collection in your size: {n} | مجموعة «{name}» الجديدة بمقاسك: {n} |

### 3.6. Срок жизни, отписка, удаление

| Когда | Что |
|---|---|
| человек выключил, «Удалить всё «Моё»», выход из аккаунта | `sub_del` — сразу |
| 90 дней без `sub_put` (приложение продлевает раз в 7 дней при открытии) | удалить сам; без «вернитесь» |
| APNs ответил `410` (`Unregistered`, `ExpiredToken`), `400` `BadDeviceToken`, `DeviceTokenNotForTopic` | удалить (приложение удалено или токен чужой) |
| ключ `fit_subs` выключен | рассылку остановить; выключен 30 дней подряд — удалить все записи |

### 3.7. Хранение (пример, MySQL; имена — ваши)

```sql
CREATE TABLE fit_subs (
  sid_hash   BINARY(32) PRIMARY KEY,                -- sha256(sid); сам sid не хранится
  token_enc  VARBINARY(512) NOT NULL,               -- токен APNs, зашифрован ключом рассылки
  token_mac  BINARY(32) NOT NULL UNIQUE,            -- HMAC-SHA256(token, ключ рассылки): «один телефон — одна подписка»
  env        ENUM('prod','sandbox') NOT NULL DEFAULT 'prod',
  lang       CHAR(2) NOT NULL, tz VARCHAR(32) NOT NULL DEFAULT 'Asia/Almaty', city VARCHAR(64) NULL,
  want       VARCHAR(4000) NOT NULL,                -- тело §2.1 после проверки
  daily      TINYINT NOT NULL DEFAULT 1, quiet_from TINYINT NOT NULL DEFAULT 22, quiet_to TINYINT NOT NULL DEFAULT 9,
  created_on DATE NOT NULL, put_on DATE NOT NULL, exp_on DATE NOT NULL,
  last_check DATETIME NULL, sent_on DATE NULL, sent_n TINYINT NOT NULL DEFAULT 0
);
CREATE TABLE fit_subs_seen (sid_hash BINARY(32) NOT NULL, listing_id VARCHAR(32) NOT NULL, seen_on DATE NOT NULL,
  PRIMARY KEY (sid_hash, listing_id));
-- по желанию, для скорости: ключи значений → подписки (те же данные, тот же срок)
CREATE TABLE fit_subs_keys (k VARCHAR(96) NOT NULL, sid_hash BINARY(32) NOT NULL, PRIMARY KEY (k, sid_hash));
```

- **Ни `user_id`, ни IP, ни `User-Agent`**, ни времени точнее дня у создания.
- **Не связывать** с аккаунтами: токен тот же, что приходит в `api/push_register.php`, — по нему **не искать** и не
  сравнивать с таблицей токенов аккаунтов; в рассылке — ни одного запроса к пользователям. Это обещание держится не
  только словом: ключ рассылки (шифр токена и HMAC) — только у задания рассылки и `api/for_mine.php`; код кабинета и
  аккаунтов к `fit_subs*` не обращается; выгрузки и отладка — без `token_enc`.
- Журнал рассылки — первые 8 знаков `sid_hash`, число находок, ответ APNs; без значений и текста; 30 дней.

### 3.8. Отказы

`{ "ok": false, "error": "…" }` с HTTP 200; кривой JSON — 400 `bad_json`; не POST — 405; тело > 8 КБ — 413; частота —
429 (10 `sub_put` в час на `sid`, 300 в час с адреса — у операторов за одним адресом тысячи телефонов).

| `error` | Когда | Приложение |
|---|---|---|
| `bad_sid` | не 32 hex | новый `sid`, повтор один раз |
| `bad_token` | не hex или не та длина | переждать новый токен |
| `fit_empty` | ничего принимаемого не осталось | «Пока не о чем сообщать — дополните «Моё»» |
| `not_found` | `sub_get` с незнакомым `sid` | считать выключенной |
| `off` | ключ `fit_subs` выключен | спрятать переключатель, оставить «N новых» |

**Готово, когда:** `sub_put` сохраняет, `sub_get` отдаёт то же с `daily` ≤ `fit_subs_daily` и тишиной не уже 22–9;
`fit_me` — `fit_empty`; `sub_del` удаляет сразу; тестовый телефон получает один push в сутки и не в тишину, только с
`ok` и `adapt`; в таблице нет столбцов `user`, `ip`, `agent`. **Проба:** §12, «§3».

### 4.1. `GET /api/for_mine.php?action=season&lang=ru`

Без куков, `Cache-Control: public, max-age=86400`, `ETag` по `v` (на `If-None-Match` — 304).

```json
{ "ok": true, "v": "2026-10-17-1", "tz": "Asia/Almaty",
  "rules": [
    { "key": "tyres_winter", "from": "10-01", "to": "11-30", "w": 3, "cats": ["tires-wheels", "tire-service"],
      "std": "tyre_season:winter_studded,winter_friction" },
    { "key": "tyres_summer", "from": "03-15", "to": "05-15", "w": 3, "cats": ["tires-wheels", "tire-service"],
      "std": "tyre_season:summer" },
```

### 4.2. Правила — встроены в приложение 83 те же

| `key` | Даты | Разделы | Чьё |
|---|---|---|---|
| `tyres_winter` | 01.10–30.11 | шины и шиномонтаж, зимние первыми | владелец |

## 5. Коллекции магазинов

### 5.1. Поле `collection`

```json
{ "category": "mens-outerwear", "brand": "Zara", "title": "Пуховик мужской", "storage": "50", "size_sys": "INT",
  "size_avail": ["48", "50", "52"], "color": ["navy"],
  "collection": { "name": "Осень-зима 2026", "season": "aw", "year": 2026 } }
```

| Поле | Формат | Что |
|---|---|---|
| `collection.name` | ≤ 60 знаков | метка партии магазина: «Осень-зима 2026», «Новая партия зимних шин» |
| `collection.season` | `ss` (весна-лето) · `aw` (осень-зима) · `all` | для порядка по сезону |
| `collection.year` | 2020…2100 | |

- Приходит в `submit`, `edit_item`, строке импорта, `batch` (§1.6), фиде (§1.4). `edit_item`: поля нет — не трогать,
  `null` — снять. Без ссылок, контактов, капса — как название.
- Сервер ведёт ключ коллекции: бренд + `season` + `year` (имя — только подпись: у магазинов оно разное) — объявления
  разных магазинов одного бренда и сезона — одна коллекция. Без бренда (своя партия магазина) — магазин + `season` +
  `year`.
- Выдача: `collection` плоско и в `specs` — «Коллекция» · «Коллекция» · «Collection» · «المجموعة»; **`collection_new:
  true`**, если коллекция впервые появилась на Kliko за последние 30 дней.

### 5.2. «Новая коллекция в вашем размере у брендов, что вам впору»

- Фильтр **`collection=new`** (публичный, в адресе) — только объявления с `collection_new`. С `size` в теле POST (§2)
  — «новая коллекция в моём размере» по всей базе.
- **Бренды на сервер не уходят.** Телефон сам поднимает бренды, которые есть в гардеробе и в заметках посадки («Nike —
  беру EU 43», `MyThings/MyThingsWardrobeModel.swift`); размер такого бренда телефон добавляет в `size` как ещё одну
  часть ИЛИ — без имени бренда.
- Push: если ≥ 3 находок подписки §3 из одной коллекции — текст `fn_coll` («Новая коллекция «Осень-зима 2026» в вашем
  размере: 14»); `{name}` — из объявлений (публичное). Брендов подписки сервер не знает: «у брендов, что вам впору»
  телефон отбирает при открытии.

**Готово, когда:** `collection` сохраняется и отдаётся; `collection=new` даёт только `collection_new: true`.
**Проба:** §12, «§5».

## 6. Магазину — обезличенный спрос

### 6.1. `GET /kz/ru/cabinet.php?action=demand&cat=tires-wheels&city=Астана&lang=ru`

Только аккаунт магазина (как `shop_required` у импорта), куки.

```json
{ "ok": true, "updated": "2026-10-17T03:00:00+05:00", "min": 20, "step": 10, "city": "Астана",
  "rows": [ { "label": "Шины 205/55 R16", "key": "tyre_size:205/55R16", "n": "40+", "n_kz": "350+", "trend": "up" },

  "note": "Сколько человек ждут новинки этого стандарта. Меньше 20 не показываем" }
```

### 6.2. Правила — k-анонимность

| Правило | Значение |
|---|---|
| Источник | **только действующие подписки §3** (один телефон — одна подписка — один голос, `token_mac`). Тела POST §2, просмотры, поиски — нет |
| Накрутка | в сводку — только подписки, чей токен APNs хоть раз принял (`200`: доставка находок или тихая проверка `apns-push-type: background` при первом `sub_put`). Иначе скрипт без входа добьёт ячейку до 19 и узнает по «20+», что в ней есть один живой человек |
| Срез | главный ключ семьи × город (или весь Казахстан) × неделя. Ключи: шины `w/h/r`, диски `r` + `pcd`, `bed_size`, VESA `pattern`, цоколь, ОЗУ `gen` + `form`, размер — таблица + значение, телефон — slug |
| Порог | ячейка < 20 — не показывать вовсе (ни «мало», ни «< 20») |
| Округление | вниз до 10: 47 → «40+» |
| Узкие срезы | никаких сочетаний (сезон × размер, размер × бренд) и своих фильтров — только фиксированные срезы выше: разницей двух ячеек человека не вычислить |
| Тренд | только если обе недели ≥ 20; `up` / `down` при изменении ≥ 20 %, иначе `null` |
| Обновление | ночная сводка в таблицу агрегатов `demand_week(key, city, week, n)`; запрос магазина к подпискам не ходит |
| Города | только областные центры и города республиканского значения; остальное — в «весь Казахстан» |
| Чего нет никогда | устройства, `sid`, времени, отдельных записей |

Пороги — в админке (по умолчанию 20 и 10). Приложение 83 спрос не показывает.

**Готово, когда:** в ответе нет ни одного `n` меньше «20+»; не магазин — `shop_required`. **Проба:** §12, «§6».

## 7. Реклама в «Для вас»

### 7.1. Правила показа

| Правило | Значение |
|---|---|
| Что | объявление продавца, оплатившего показ в «Для вас» (кампания на сайте) |
| Когда показываем | **только если подходит**: телефон по полному «Моему» дал «Подходит» (`ok`; «Нужна деталь» — нет, В5); значения — от продавца (`std_src` из `ok_from`). Доверия (§8.3) телефон не видит — продавцов со сниженным доверием по семье сервер в `ads` **не кладёт** |
| Метка | «Реклама» на карточке, всегда видна; «Почему я это вижу?» — та же причина, что у обычной карточки, и строка `ad_why` |
| Сколько | не больше 2 на ряд из 12, не на первом месте, не две подряд; на экране «Для вас» — не больше 1 на 6 карточек |
| Где нет | вещи «Моих детей» и семьи `kids_optin`; детское и опасное — `child_seat`, `toy_age`, `electric_cable`, `camping_gas`, `abrasive_disc` (кресла, игрушки по возрасту, электрика, газ, диски болгарки); push «Новинок». Не «все `safety: true`»: так помечены и `lamp_base`, `psu`, `car_battery`, `mains_plug` — у них `safety` значит «Подходит только по полям продавца», а реклама и так только по ним |

### 7.2. Кандидаты — по разделу, сверка — на телефоне

```
GET  /api/listings.php?cat=lighting&per=48&sort=new&ads=fit          (путь «Для вас» через GET по разделам)
POST /api/listings.php?per=48&sort=new&ads=fit   { …тело §2.1… }     (путь §2)
→ { "ok": true, "items": [ … ], "ads": [ { "id": "e1f2a3", "ad": "c77", "category": "lighting",
                                          "std": { "lamp_base": { "base": "E14" } }, "…": "поля карточки, как у items" } ] }
```

- `ads` — до 20 кандидатов на раздел: **по разделам (`cat` / `cats`), городу и дню**. Из тела для выбора рекламы —
  **только `cats`**; `fit_*`, `size` и куки **не читать**: одинаковые `cats` с разным «Моим» → одинаковые `ads` (проба
  §12).
- Телефон сверяет кандидатов сам и показывает только подходящих. Сервер **не узнаёт**, что подошло и что показано.
- Учёт: показов не считаем, маяков нет. Оплата — за дни кампании (как дни ТОП); переходы — нажатие открывает
  объявление с `src=fa` (как `src=ss` у сохранённых поисков), сумма переходов по кампании в день — продавцу в кабинете.
- Переход `src=fa` говорит «эта вещь подошла к «Моему»» — поэтому только `+1` к счётчику кампании за день: не к
  аккаунту, устройству и IP, не в историю просмотров, не в рекомендации. Анкета — §10.2, решение — В11.

## 8. Неверные стандарты: кто отвечает

### 8.1. Модерация

Как `SERVER_STANDARDS.md` §9: `std` — из каталога или правдоподобное; набивка ради выдачи («все VESA», 20 цоколей,
«все сокеты») — как спам в названии; `fit_match` — только расчёт сервера. Для импорта — код `stuffing` в отчёте (§1.5)
и семья отбрасывается.

### 8.2. «Не подошло?» — жалоба без «Моего»

```
POST /report.php?action=submit { "csrf": "…", "target_id": "<продавец>", "listing_id": "a1b2c3",
                                 "reason": "std_mismatch", "std_fam": "tyre_size", "level_shown": "ok", "comment": "" }
```

- `reason: "std_mismatch"` — «Не соответствует указанному стандарту» (уже в `SERVER_STANDARDS.md` §9); новые —
  **`std_fam`** (какая семья, ключ каталога) и **`level_shown`** (что показало приложение: `ok`, `adapt`).
- **Значений «Моего» в жалобе нет** — ни размеров, ни машины. `comment` пишет сам человек. Но жалоба идёт от
  аккаунта, и `level_shown: "ok"` у шин 205/55 R16 говорит «у человека подходящая машина» — это его действие по
  нажатию: `std_fam` и `level_shown` — только модерации и `std_trust`, не в профиль, рекомендации и рекламу.
- После сделки — прежние пути: спор `std_mismatch`, возврат `nofit` (`SERVER_CIRCLE.md` §8.3).

### 8.3. Доверие к стандартам продавца — ниже в выдаче

Внутренний счёт `std_trust` по продавцу и семье. Считаются **только подтверждённые** модератором `std_mismatch` и
возвраты `nofit` с `return_fault: "seller"` — жалобы конкурентов сами по себе ничего не меняют.

| За 90 дней по семье | Что |
|---|---|
| 1 подтверждённая | письмо продавцу: объявление, семья, как исправить |
| 3 подтверждённые или ≥ 20 % ошибок проверки импорта по семье | значения продавца по семье — **не лучше `check`** в §2; в подписки §3 и рекламу §7 не идут |
| 5 и больше | семья скрыта у всех его объявлений на 30 дней («Проверьте» у покупателя), разбор модератором |
| 90 дней без подтверждённых | счёт обнуляется |

Продавец видит своё состояние в кабинете и может обжаловать в поддержке. Наружу `std_trust` не отдаётся — только
`fit_match.level`. Поэтому телефон берёт **худший** из своего уровня и `fit_match` (§2.2); на пути GET (без `fit_*`,
`std_server_fit` выключен) снижение доходит до покупателя только через подписки, рекламу и скрытие семьи (5+).

**Готово, когда:** `std_mismatch` со `std_fam` принимается; после трёх подтверждённых у продавца в §2 нет `ok` по этой
семье. **Проба:** §12, «§8».

### 10.2. App Privacy — до включения `fit_subs` (владелец)

- Подписка хранит значения на сервере — это «сбор». Мы её с человеком не связываем, но хранится она рядом с токеном
  push, а тот же токен у сервера уже связан с аккаунтом (`api/push_register.php`): по правилам Apple это «можно
  связать». Поэтому честно и проще — **«Search History — Linked to You — App Functionality»**: та же строка уже нужна
  сохранённым поискам (`SERVER_CIRCLE.md` §6.8), одна на оба. В манифесте — §9. Если спрос магазинам (§6) строится из
  подписок — ещё цель «Other Purposes» (В3).
- Токен push уже объявлен (`NSPrivacyCollectedDataTypeDeviceID`, связан, App Functionality), город — «Coarse

- `std_server_fit`, `season_rules` анкету не меняют: тело POST не хранится, сезон — публичный.
- `fit_ads`: выбор рекламы — на телефоне, но сумма переходов `src=fa` — это «Product Interaction» для рекламы

  (В11) — анкета не меняется.

## 16. В обе стороны: от покупателя к продавцу

Слова владельца, 17.10.2026:

> «я просто хотел бы, чтобы этот самый механизм работал на пользу юзеру от продавца к покупателю и наоборот» → «да, …
> пачкой в 83»

§1–8 — от продавца к покупателю: магазин залил товар, человек узнал сам. Здесь — обратно: тот же механизм (значения
стандартов, подписки §3, отбор §2, сводка §6) помогает продавцу найти тех, кому вещь подойдёт, а покупателю — сказать,
что он ищет. Имён по-прежнему нет ни в одну сторону.

```
 ПОКУПАТЕЛЬ (телефон, «Моё»)                    СЕРВЕР ultra-site                           ПРОДАВЕЦ
 подписка §3: только значения ─────────► сводка §6: ≥ 20, вниз до 10 ───16.1──► подача: «Подойдёт 40+ людям в Астане»
 push «Новое под вашу машину» ◄───16.2── одно объявление × подписки, лимиты §3 ◄── «Сообщить им» (бесплатно, один раз)
 «Ищу зимние шины 205/55 R16 до 80 000 ₸» ─16.3─► wanted_put → подходящим объявлениям ─► «Есть покупатель» (без имени)
 отклики: объявление + слово ◄─────────────────── request_action respond ◄────────────── отклик своим объявлением
 «Ответить» → обычный чат: первым пишет покупатель — с этого сообщения продавец его видит
 вещь «Моего» → «Продать своё» ───16.4──► submit: std · parts · from: "my" · relist_from ──► сразу к подпискам (16.2)
```

Польза обеим сторонам: меньше «а подойдёт?», возвратов и споров; продавец продаёт быстрее, покупатель находит точнее.
Гарант-сделка закрывает деньги, «Подходит» — совместимость.

### 16.1. Спрос при подаче: «Подойдёт N людям в <город>»

`POST /kz/ru/cabinet.php?action=fit_demand` — куки и `csrf`, **любой вошедший** (не только магазин, как в §6). Тело —
поля будущего объявления под теми же именами, что у `submit` (§1.1):

```json
{ "csrf": "…", "category": "tires-wheels", "city": "Астана", "lang": "ru",
  "parts": { "kind": "tire", "width": "205", "profile": "55", "diameter": "16", "season": "winter_studded" },
  "std": { "tyre_load_index": { "li": 94 } } }
→ { "ok": true, "updated": "2026-10-17T03:00:00+05:00", "min": 20, "step": 10, "city": "Астана",
    "rows": [ { "key": "tyre_size:205/55R16", "for": "car", "label": "Шины 205/55 R16", "n": "40+", "n_kz": "350+" } ],
    "wanted": 3, "notify": true }
```

| Поле | Что |
|---|---|
| `rows` | ячейки сводки §6 по главным ключам семей этого объявления (§6.2, «Срез»): шины — `w/h/r`, кровать — `bed_size`, одежда — таблица + значение… Обычно одна строка; шины на дисках комплектом — две. Ячейка < `min` — **строки нет** |
| `for` | чья это вещь у подписок: `car`, `phone`, `laptop`, `size`, `std:<семья>` (здесь — ключ семьи каталога, не номер группы `g` §3.5) — телефон пишет «у них машина под 205/55 R16», «у них кровать 160×200», «у них размер M» (`fd_why_car`, `fd_why_size`; `phone`, `laptop`, `std:*` — `fd_why_std`, §16.6) |
| `label` | подпись ячейки, как в §6; у размера — значение с системой («M (INT)», «EU 43») |
| `n`, `n_kz` | как §6: вниз до `step`; город и весь Казахстан; `n_kz` < `min` — `null` |
| `wanted` | открытых «Ищу» (§16.3) в этом городе, которым объявление подошло бы на `ok` по значениям (цену и `cond` не сверяет: в подаче их может ещё не быть); без порога — эти запросы покупатели сами показали продавцам (В18). `wanted_std` выключен — `0` |
| `notify` | доступно ли «Сообщить им» (§16.2): ключ включён, у вещи есть стандарт не из текста, у продавца нет сниженного доверия по семье (§8.3), дневной предел не исчерпан |

- **Только сводка.** Ответ — из `demand_week` §6 (ночная, только подписки с принятым токеном APNs); к подпискам запрос
  не ходит. Те же пороги из админки, те же города, ни времени, ни устройств, ни отдельных записей.
- **Ключ строит сервер** из полей объявления своей нормализацией. Сочетаний нет: сезон, бренд, цена, индексы ячейку не
  сужают — «зимние 205/55 R16» и «все 205/55 R16» — одна ячейка, иначе разницей двух ответов человек вычислился бы
  (§6.2, «Узкие срезы»).
- Тело — как тело §2 (§2.4): не в журналы, отладку, БД и аналитику, не хранить; аккаунт — только для входа и счётчика
  частоты. До публикации это ещё не объявление, а в «Продать своё» (§16.4) — значения вещи «Моего». Ответ —
  `Cache-Control: private, no-store`.
- Нет стандарта или раздел без семей — `ok`, `rows: []`, `wanted: 0`, `notify: false`. Не вошёл — `auth`, ключ
  выключен — `off`.
- Частота: 30 в час и 200 в сутки на аккаунт (429). Телефон спрашивает при смене ключа (раздел, город, значения), не
  чаще раза в 3 с.
- Включать не раньше двух недель `fit_subs` (как `demand_stats`), но от `demand_stats` ключ не зависит.

**Готово, когда:** в ответе нет `n` меньше «20+»; сезон не меняет ответ; гостю — `auth`. **Проба:** §12, «§16.1».

### 16.2. «Сообщить им»: push подходящим подпискам после публикации

`submit` принимает **`fit_notify: true`** — выбор продавца (переключатель в подаче, В13), на одно объявление.

| Правило | Значение |
|---|---|
| Где | только `submit` (в том числе «Продать своё», §16.4). В `edit_item`, `ai_import_publish`, `batch`, фиде поля нет: товар магазинов и так идёт в сводки §3 |
| Когда | после **одобрения** модерацией. Сервер сразу, не дожидаясь цикла 1–3 часа (§3.1), сверяет **это одно** объявление с подписками §3 тем же отбором §2. Сверяет **задание рассылки** (ключ рассылки — только у него, §3.7): событие одобрения лишь ставит номер объявления в его очередь; код кабинета и модерации к `fit_subs*` не обращается, обратно в объявление задание пишет только `fit_notified_on` и округлённое `n` |
| Кому | подпискам, у которых объявление — **`ok`**; `universal` у чехлов (отбор `fit_level: ok` его не берёт, `SERVER_MY_THINGS.md` §3.1, а push ушёл бы всем подпискам с телефоном), `adapt`, `check`, из текста и примерного (`std_src` `text`, `tpl`) — нет; город — как §3.4. Продавец со сниженным доверием по семье (§8.3) — поле игнорируется |
| Лимиты push | **общие с §3**, не сверх: этой подписке сегодня push ещё не было и сейчас её окно (§3.4) — push сейчас; иначе объявление — обычная находка ближайшей отправки §3.4, в одной сводке. `daily`, тишина, окно 10–21, `fit_subs_seen` — как §3 |
| Один раз | на объявление: `fit_notified_on`. Правка, поднятие, смена цены, снятие и подача заново в течение 30 дней (§3.4), тот же `relist_from` или `ext_id`, новая подача того же продавца с тем же ключом (раздел и значения, как §16.1) за 30 дней — повторно не шлют |
| Не занять человека | одной подписке — не больше одного такого push от одного продавца за 7 дней; дальше — в сводку. Считать по `fit_subs_seen` (номера объявлений этого продавца с `fit_notified_on` за 7 дней) — отдельной связи «подписка — продавец» не хранить |
| Продавцу | до 5 объявлений с `fit_notify` в сутки (магазину — 20, В14); сверх — поле игнорируется, объявление публикуется, состояние `limit` |
| Деньги | **бесплатно и не продаётся** (В15): платная рассылка — это реклама (§7) и покупка Apple (правило 3.1.1, §7.3). Продавец не выбирает получателей и не платит — push идёт по подписке и согласию человека (§10.3) |

Push — тот же `fit_new` §3.5 (тип, категория `FIT_NEW`, заголовки APNs, `url`): телефону нового разбора не нужно.

```json
{ "aps": { "alert": { "title": "Новое под вашу машину",
                      "body": "Шины 205/55 R16 · зимние шипованные · 240 000 ₸ за 4 шт" },
           "thread-id": "fit_new", "category": "FIT_NEW", "sound": "default" },
  "type": "fit_new", "url": "/cabinet.php?go=foryou&new=1", "ids": ["a1b2c3"], "g": ["car"], "n": 1 }
```

- В push одна находка (`n: 1`) — заголовок по виду группы `g` (`fn1_*`, §16.6), тело — подпись и цена объявления,
  собранные как `fn_from` §3.5, но без «от»: цена одна. Находок больше — обычная сводка `fn_title`, `fn_body`.
- Объявление только что одобрено — оно в первой странице `sort=new` своего раздела, которую «Для вас» и так грузит без
  куков; отдельного запроса по номеру нет (§3.5).
- Своё объявление продавец может получить сам, если у него подписка с тем же значением: сервер подписку с аккаунтом не
  связывает (§3.7) и связывать ради этого не должен; телефон своё при открытии не показывает.

`my_items` (владельцу) — состояние и число:

```json
"fit_notify": { "state": "sent", "n": "20+", "on": "2026-10-17" }, "wanted": 2
```

| `state` | Что |
|---|---|
| `queued` | ждёт одобрения и сверки заданием рассылки |
| `sent` | сверено со всеми подписками: push ушли сейчас или уйдут в сводке |
| `skipped` | + `why`: `no_std` (нет стандарта), `text` (значения из текста), `trust` (§8.3) |
| `limit` | дневной предел продавца |

- `n` — сколько подписок получат объявление (сейчас или в сводке), по правилам §6: считаются только подписки с принятым
  токеном (§6.2, «Накрутка»), вниз до 10, меньше 20 — `null`, и при нуле тоже `null`: 0 и 19 не различить. Ни городов,
  ни времени, ни устройств.
- `wanted` — число открытых «Ищу» (§16.3), которым подходит это объявление: «Есть покупатель · 2».
- Хранение — три поля объявления: `fit_notify`, `fit_notified_on`, `fit_notify_n`.

**Готово, когда:** после одобрения тестовый телефон с подходящей подпиской получает один push с `n: 1` и не в тишину;
правка не шлёт снова; `adapt` — только в сводке; `n` ниже 20 — `null`. **Проба:** §12, «§16.2».

### 16.3. «Ищу» со стандартами

Покупатель говорит, что ищет («Ищу зимние шины 205/55 R16 до 80 000 ₸ · Астана»); продавцы с подходящими объявлениями
видят «Есть покупатель» и откликаются своим объявлением; покупатель видит отклики и сам отвечает в чат. По образцу
«Заявок рядом» — с тремя отличиями: по стандарту, 30 дней, без имени.

#### 16.3.1. Чем отличается от «Заявок рядом»

| | «Заявки рядом» (как сейчас) | «Ищу» |
|---|---|---|
| Создаёт | `broadcast.php {text, section, specialty, city, lat, lon, radius_km}` | `cabinet.php?action=wanted_put`: `want`, раздел, город, цена; без точки и радиуса |
| Кому | продавцы и мастера в радиусе 2 км или в городе | продавцы с живым объявлением, подходящим на `ok` (§2), в городе запроса |
| Живёт | 5 минут (`seconds_left`) | 30 дней |
| Получатель видит | имя, телефон, адрес, точку клиента | текст запроса, значения, цену, город, день — **ни имени, ни телефона, ни аккаунта** |
| Отклик | `respond` → переписка мастера с клиентом | `respond` своим объявлением и словом → карточка у покупателя; переписки нет, пока покупатель не ответит |
| Список получателя | `my_requests` | `my_requests&kinds=wanted` |
| Список автора | карточка в его переписке | `my_wanted` (новое) |

Почему создание — не `broadcast.php`: прежний `broadcast.php` неизвестное поле `kind` пропустит и разошлёт запрос
по-старому, с именем и телефоном. Новый адрес на старом сервере — просто «не поддерживается» (§0).

#### 16.3.2. Создать: `POST /kz/ru/cabinet.php?action=wanted_put`

```json
{ "csrf": "…", "section": "tires-wheels", "city": "Астана", "lang": "ru",
  "want": { "fit_car": "tyre:205/55R16", "std": "tyre_season:winter_studded,winter_friction" },
  "pmin": null, "pmax": 80000, "cond": "", "note": "Комплект, можно б/у" }
→ { "ok": true, "rid": "w5521", "status": "open", "text": "Ищу зимние шины 205/55 R16 до 80 000 ₸ · Астана",
    "exp": "2026-11-16", "count": 7 }
```

| Поле | Что |
|---|---|
| `want` | **одна вещь**: ровно один вид §2.1 и одна группа — `fit_car` (шины `tyre:` одним размером или диск `r:` + `pcd:`, по желанию `dia:`, `et:`), `fit_std` (одна группа, без `\|`), `size` (одна часть взрослых таблиц), `fit_phone` (один slug), `fit_laptop`; по желанию `std` — публичный фильтр одной вещи (`SERVER_STANDARDS.md` §4.1): сезон шин, тип матраса |
| `section` | раздел из `cats` семьи; обязателен |
| `city` | город названием; `""` — весь Казахстан |
| `pmin`, `pmax`, `cond` | как у `subs.php?action=add`: целые ₸; `new`, `used` или пусто |
| `note` | по желанию, ≤ 140 знаков; модерация как у названий: без телефонов, ссылок, мессенджеров, имён |
| `rid` | есть — правка своего запроса: `pmin`, `pmax`, `cond`, `note` (снова на модерацию); `want`, `section`, `city` не меняются — это новый запрос |
| ответ `text` | **собирает сервер** из значений (подписи по `line` семьи и `parts`, как push §3.5) на языке того, кто смотрит; ровно его увидят продавцы. Телефон до отправки показывает тот же текст (`wt_text`, `wt_upto`, `wt_consent`) |
| ответ `count` | сколько продавцов с подходящими живыми объявлениями увидят запрос сейчас (объявления и так публичны); 0 — запрос ждёт новых подходящих все 30 дней |
| ответ `status` | `open` или `moderation` (сомнительный `note`, новый аккаунт) |

- Это не «Моё» целиком и не подписка: одна вещь, которую человек сам выбрал и прочитал текстом перед отправкой, — как
  объявление «Куплю». Поэтому значения в виде `fit_*` здесь можно, хотя в `subs.php` нельзя (`SERVER_MY_THINGS.md`
  §3.1): запрос — его публикация, а не профиль.
- **Никогда:** `fit_me`, `fit_kids`, семьи `fit_std: false` и `"kids_optin"`, детские таблицы размеров, VIN, госномер,
  марка и модель машины. Пришло — **отказ** `want_bad` с `bad: ["fit_me"]`: запрос, который увидят люди, молча не правим.
- Только вошедший (`auth`). Гостю приложение делает «Ищу» сохранённым поиском на телефоне (§16.3.8, В19).
- О новых подходящих объявлениях «Ищу» покупателю не сообщает — это подписка §3 или сохранённый поиск; «Ищу» приносит
  отклики.

| `error` | Когда |
|---|---|
| `auth` | не вошёл |
| `want_bad` | не одна вещь, запрещённое, раздел не из `cats` семьи; `bad` — что именно |
| `note_bad` | контакты, ссылки, стоп-слова; `msg` — как правильно |
| `dup` | открыт такой же (`want`, `section`, `city`) — `rid` прежнего |
| `limit` | больше 5 открытых или 10 новых за сутки |
| `off` | ключ `wanted_std` выключен |

#### 16.3.3. Продавцу: «Есть покупатель» — `my_requests&kinds=wanted`

```
GET /kz/ru/cabinet.php?action=my_requests&me_id=<я>&kinds=wanted
→ { "ok": true, "new": 2, "requests": [
    { "rid": "w5521", "kind": "wanted", "eff_status": "open", "seconds_left": 2505600, "at": "2026-10-17",
      "text": "Ищу зимние шины 205/55 R16 до 80 000 ₸ · Астана", "note": "Комплект, можно б/у", "city": "Астана",
      "section": "tires-wheels", "pmax": 80000,
      "item_id": "a1b2c3", "item_title": "Michelin X-Ice North 4 205/55 R16", "item_img": "https://…",
      "items": ["a1b2c3", "b2c3d4"], "i_responded": false, "responses": 3 } ] }
```

- Поля — те же, что у `requests[]` «Заявок рядом» (приложение читает их тем же разбором, `Заявка`), плюс `kind`,
  `note`, `section`, `pmax`, `items`. `item_*` — **моё** подходящее объявление (первое), `items` — все мои подходящие.
  `seconds_left` — до конца 30 дней; `at` — только день.
- **Полей `client_id`, `client_name`, `client_phone`, `client_address`, `client_lat`, `client_lon` нет вовсе** — ни у
  одного `kind: "wanted"`, даже пустыми. Аккаунт автора знают только модераторы.
- Без `kinds` — ответ **прежний**, «Ищу» в него не попадают: установленные сборки и сайт показывают «Заявки рядом» как
  сейчас. `kinds=wanted` — только «Ищу».
- Видит продавец, у которого есть живое одобренное объявление, подходящее на `ok` (отбор §2 с `fit_level: "ok"`, цена
  в `pmin`…`pmax`, `cond`, город запроса; доставка по стране — У10). Своё «Ищу» — не видит; продавцы со сниженным
  доверием по семье (§8.3) — не видят; продавец, которого автор заблокировал (`subs.php?action=block`), или который
  заблокировал автора, — не видит и откликнуться не может (`not recipient`). Новое подходящее объявление появилось
  позже — запрос появляется и у него.
- Push продавцу — к аккаунту (`api/push_register.php`, как чат): `type: "wanted_seller"`,
  `url: "/cabinet.php?go=requests&kind=wanted"`; одна сводка в сутки на продавца, окно 10:00–21:00, не в тишину 22–9.
- Push к аккаунту дойдёт и до установленных старых сборок (токен в `push_register.php` — без версии), и они откроют
  `url` страницей кабинета: сайту понимать `?go=requests&kind=wanted` и `?go=wanted&rid=` (§16.3.5) — показать «Ищу»
  страницей или хотя бы открыть кабинет, как `?go=foryou` (§3.5).

#### 16.3.4. Действия: `POST /kz/ru/cabinet.php?action=request_action`

Тот же адрес и те же `act`, что у «Заявок рядом» (`Inbox/RequestsModel.swift`), для `rid` вида `wanted`. Кто что
шлёт — по `kind` запроса: в «Заявках рядом» `accept` («Принять заказ») — у мастера, здесь `accept` — у автора запроса;
`confirm` — у автора в обоих, но здесь с `rsp`, а не `master_id`.

| `act` | Кто | Тело | Ответ | Что |
|---|---|---|---|---|
| `respond` | продавец | `rid`, **`listing_id`**, **`msg`** (≤ 300, по желанию) | `{ok, rsp}` — **без** `client_id` | отклик: моё объявление и слово → у покупателя в `my_wanted`, push ему. Переписка не открывается |
| `report` | продавец | `rid` | не читается | «Скрыть», как сейчас (прячет сразу), и сигнал модерации |
| `report` | покупатель | `rid`, **`rsp`** | не читается | скрыть отклик и пожаловаться (не то, спам) |
| `accept` | покупатель | `rid`, `rsp` | `{ok, seller_id, seller_name, ctx}` | «Ответить»: открыть обычную переписку с продавцом по объявлению отклика (`ctx` — его номер), как `respond` заявок открывает её мастеру. **Первым пишет покупатель** — с этого сообщения продавец видит его в чате, как любого покупателя |
| `confirm` | покупатель | `rid`, `rsp` по желанию | `{ok}` | «Нашёл» или «Больше не ищу»: запрос `closed`, у продавцов пропадает; `rsp` — только статистика, продавцу ничего |
| `delete` | покупатель | `rid` | `{ok}` | удалить запрос и все отклики сразу |

Отказы — прежние коды «Заявок рядом» (приложение их уже переводит: `closed`, `cap`, `expired`, `not recipient`,
`not client`) — что они значат для «Ищу» — и новые `not_fit`, `dup`, `limit`, `msg_bad`:

| `error` | Когда |
|---|---|
| `not recipient` | продавцу этот запрос не показывается (нет подходящего объявления, блокировка, §16.3.3) |
| `not client` | не автор запроса |
| `not_fit` | `listing_id` не его, не живое или не подходит запросу на `ok` |
| `dup` | с этим объявлением уже откликался |
| `cap` | у запроса 20 откликов; или от этого продавца — уже 2 объявления |
| `limit` | у продавца больше 30 откликов за сутки |
| `msg_bad` | контакты, ссылки в `msg` |

- Продавцу о покупателе — ничего: ни `seen`, ни `accepted`, ни «был в сети» — до его первого сообщения в чате.
- Телефон покупателя — никогда: в переписке — как сейчас, только если человек сам его напишет.

#### 16.3.5. Покупателю: `GET /kz/ru/cabinet.php?action=my_wanted`

```json
{ "ok": true, "new": 1,
  "wanted": [ { "rid": "w5521", "status": "open", "text": "Ищу зимние шины 205/55 R16 до 80 000 ₸ · Астана",
                "note": "Комплект, можно б/у", "section": "tires-wheels", "city": "Астана",
                "want": { "fit_car": "tyre:205/55R16", "std": "tyre_season:winter_studded,winter_friction" },
                "pmin": null, "pmax": 80000, "cond": "", "created": "2026-10-17", "exp": "2026-11-16", "count": 7,
                "responses": [ { "rsp": "r91", "listing_id": "a1b2c3", "seller_id": "u77", "seller_name": "ШинЦентр",
                                 "price": 76000, "msg": "Есть комплект, DOT 2025", "at": "2026-10-17",
                                 "seen": false, "accepted": false, "gone": false } ] } ] }
```

- `status`: `moderation`, `open`, `closed`, `expired`, `rejected` (+ `why` — текст модератора).
- Отклик — публичное объявление продавца (карточку телефон грузит обычным `?ids=`) и его слово; `gone: true` —
  объявление снято или продано.
- `new` — непросмотренных откликов; `seen` ставит открытие запроса (`my_wanted&rid=w5521`); продавцу не виден.
- Отклики продавца, которого покупатель заблокировал (`subs.php?action=block`; `blocked` в `status`), не показываются и
  push не дают.
- Push покупателю — к аккаунту: `type: "wanted_rsp"`, `url: "/cabinet.php?go=wanted&rid=w5521"`; первый отклик —
  сразу (в окне 10:00–21:00, иначе утром), дальше — не больше одного в сутки на запрос, сводкой.

#### 16.3.6. Срок, модерация, лимиты

| Когда | Что |
|---|---|
| 30 дней от создания | `expired`: у продавцов пропадает; автору видно ещё 30 дней, потом — удалить с откликами |
| `confirm` | `closed`: у продавцов пропадает; автору — до срока |
| `delete`, удаление аккаунта | сразу, с откликами |
| объявление отклика снято, продано | отклик `gone`, не удаляется |
| модератор отклонил | `rejected`, продавцам не показывается |

Продления нет: «Ищу снова» в приложении — новый `wanted_put` теми же полями.

| Предел | Значение |
|---|---|
| Покупатель | ≤ 5 открытых, ≤ 10 новых в сутки; тот же `want` + `section` + `city` открыт — `dup` |
| Запрос | ≤ 20 откликов; от одного продавца — ≤ 2 объявлений |
| Продавец | ≤ 30 откликов в сутки; один отклик на пару «запрос × объявление» |
| Push | продавцу — 1 сводка в сутки; покупателю — первый отклик сразу, дальше 1 в сутки на запрос; тишина 22–9 |
| Частота | `wanted_put` — 20 в час на аккаунт; `my_requests&kinds=wanted`, `my_wanted` — 60 в час (429) |

Модерация — тот же конвейер, что у названий и описаний (§8.1, У12): стоп-слова, контакты, запрещённые разделы — как у
подачи; «ищу всё» не пройдёт само — `want` всегда одна вещь. Жалобы `report` обеих сторон — модератору; три
подтверждённые жалобы на отклики продавца за 30 дней — его отклики на «Ищу» закрыты на 30 дней. Пользовательский
контент с жалобой и блокировкой — правило App Review 1.2.

#### 16.3.7. Хранение (пример, MySQL; имена — ваши)

```sql
-- если заявки «Заявок рядом» уже в своей таблице — те же столбцы туда, с kind = 'wanted'
CREATE TABLE wanted (
  rid        VARCHAR(16) PRIMARY KEY,
  user_id    INT NOT NULL,                          -- автор: модерации и ему самому; продавцам — никогда
  section    VARCHAR(64) NOT NULL, city VARCHAR(64) NULL,
  want       VARCHAR(1000) NOT NULL,                -- одна вещь после проверки §16.3.2
  pmin INT NULL, pmax INT NULL, cond VARCHAR(8) NOT NULL DEFAULT '',
  note       VARCHAR(140) NULL, lang CHAR(2) NOT NULL,
  status     ENUM('moderation','open','closed','expired','rejected') NOT NULL,
  created_on DATE NOT NULL, exp_on DATE NOT NULL
);
CREATE TABLE wanted_rsp (
  rsp VARCHAR(16) PRIMARY KEY, rid VARCHAR(16) NOT NULL, listing_id VARCHAR(32) NOT NULL, seller_id INT NOT NULL,
  msg VARCHAR(300) NULL, at DATE NOT NULL, seen TINYINT NOT NULL DEFAULT 0, accepted TINYINT NOT NULL DEFAULT 0,
  hidden TINYINT NOT NULL DEFAULT 0, UNIQUE KEY (rid, listing_id)
);
-- для отбора «кому показать»: ключи значений → запросы, как fit_subs_keys (§3.7)
CREATE TABLE wanted_keys (k VARCHAR(96) NOT NULL, rid VARCHAR(16) NOT NULL, PRIMARY KEY (k, rid));
```

- `text` не хранится: его собирают из значений на языке того, кто смотрит.
- `want` — не в аналитику, рекомендации и рекламу; в журналах — как объявления.
- **«Ищу» и подписки §3 между собой не сверять** — ни для `count`, ни для дублей, ни для сводки §6: `wanted` связан с
  аккаунтом, и совпадение редких значений и города связало бы с ним подписку без входа. `wanted*` — код кабинета, к
  `fit_subs*` он не обращается (§3.7); `wanted_keys` — отдельно от `fit_subs_keys`.

#### 16.3.8. До сервера: «Ищу» — сохранённый поиск со стандартом

Ключ `wanted_std` выключен или адреса нет — приложение 83 делает «Ищу» тем, что уже работает:

- Сохранённый поиск: `keyword` — подпись стандарта, как её чаще пишут в названиях (`title_examples`, `line` каталога:
  «205/55 R16», «160x200», «E14»), `category` — раздел, `city`, `pmin`, `pmax`, `cond` — ровно поля
  `subs.php?action=add` (`SavedSearch/SubsSync.swift`). У вошедшего — подписка аккаунта и существующие push сайта по
  сохранённым поискам; у гостя — поиск на телефоне и фоновая проверка `kz.kliko.app.saved-search` (одно локальное
  уведомление).
- Значения стандарта — **только в записи поиска на телефоне**: `fit_*` в `subs.php` не принимаются
  (`SERVER_MY_THINGS.md` §3.1), а `std` в `subs` — шаг Б, заменённый §3 (В1). По ним телефон сверяет находки: в локальное
  уведомление и наверх выдачи — «Подходит»; остальное ниже, не скрыто.
- Серверу ничего. Push сайта по `keyword` придёт и на неподходящее со «205/55 R16» в названии, а «205/55R16» без пробела
  `keyword` может не поймать — это временный путь.
- Ключ включён — у «Ищу» выбор: «Только мне — сохранённым поиском» или «Показать продавцам» (§16.3.2). Сохранённые
  поиски остаются как есть.

**Готово, когда:** `wanted_put` собирает `text` и отказывает в `fit_me` и контактах; продавец с подходящим объявлением
видит запрос без `client_*`, без `kinds` ответ прежний; отклик доходит до `my_wanted`; `accept` открывает переписку;
`confirm` и 30 дней убирают запрос у продавцов; `delete` — сразу. **Проба:** §12, «§16.3».

### 16.4. «Продать своё» из «Моего»

Приложение знает точные значения вещи — подача заполняется сама:

| Что | Откуда |
|---|---|
| Раздел, название | из модели и стандарта вещи, как `relist_draft.title` (`SERVER_CIRCLE.md` §4.2): без имён вещей «Моего» — не «Camry жены», не «спальня» |
| `std`, `std_src` | значения вещи; `std_src` — как у вещи: из сделки — прежний у источника (`scan`, `title`…, `SERVER_CIRCLE.md` §4.2; `deal` в `submit` не уходит — `SERVER_STANDARDS.md` §3.1), по модели устройства — `model`, введённые человеком и подтверждённые в подаче — `""` |
| `parts`, `qty` | шины и диски машины (`parts.dot`, если известен), комплект — `qty: 4`; ОЗУ — кит |
| Размеры, габариты | `storage`, `size_sys`, `size_all`, `dim_*` |
| «Куплено на Kliko» | вещь из сделки — `relist_from: "deal:<id>"` и флажок `show_provenance` (выбор продавца, `SERVER_CIRCLE.md` §4.3) |
| Состояние | `cond_grade` предлагается, не лучше снимка (`SERVER_CIRCLE.md` §3.5) |
| Фото и описание | новые: план съёмки и студия (`SERVER_CIRCLE.md` §4.6) |

```json
{ "csrf": "…", "category": "tires-wheels", "title": "Michelin X-Ice North 4 205/55 R16 94T, комплект",
  "parts": { "kind": "tire", "width": "205", "profile": "55", "diameter": "16", "season": "winter_studded", "dot": "3523" },
  "std": { "tyre_load_index": { "li": 94 }, "tyre_speed_index": { "speed": "T" } }, "std_src": "", "qty": 4,
  "from": "my", "relist_from": "deal:D-10293", "show_provenance": true, "fit_notify": true,
  "…": "фото, цена, город — как обычно" }
```

- **Нового приёма нет**: `std`, `parts`, `qty` — `SERVER_STANDARDS.md` §3.1, `SERVER_DIMENSIONS.md` 4.1; `from: "my"`,
  `relist_from`, `show_provenance` — `SERVER_CIRCLE.md` §4.3; `fit_notify` — §16.2.
- «Источник `src=my`» из ответа владельца — это **`from: "my"`** `submit`: только статистика (сколько подано из «Моего»,
  сколько из них с `fit_notify`, сколько продано); в выдачу, профиль и рекламу не идёт.
- «Сообщить им» в «Продать своё» включён по умолчанию (В13): объявление после одобрения сразу попадает к подходящим
  подпискам (§16.2). Продавец снимает одним касанием.
- «Подойдёт N» (§16.1) — сразу на первом шаге: значения уже известны. До публикации это значения «Моего» — поэтому
  тело `fit_demand` не хранится и не пишется в журналы (§16.1, как §2.4).
- Без `circle.relist` приложение собирает подачу само из вещи и снимка сделки; с ним — из черновика `relist_draft`
  (одинаковая чистка названия и цена-подсказка).

**Готово, когда:** подача со `std`, `parts`, `from: "my"` сохраняется, `from` наружу не отдаётся; с `relist_from` —
как `SERVER_CIRCLE.md` §4. **Проба:** §12, «§16.4».

### 16.5. Приватность

| Данные | Кто видит | Нельзя | Срок |
|---|---|---|---|
| Спрос §16.1 | любой вошедший при подаче — числа подписок ≥ 20, вниз до 10; число открытых «Ищу» — без порога (В18) | ячейки < 20, сочетания, время, устройства, отдельные подписки; тело запроса в журналах и БД | — (из сводки §6; тело — только запрос) |
| `fit_notify` | продавец — состояние и число по правилам §6 | кому ушло, число ниже 20, города, время доставки | как объявление |
| Push §16.2 | только подписка | продавцу — что-либо о подписке | §3 |
| «Ищу» | автор — всё; подходящие продавцы — текст, `note`, значения, цену, город, день | имя, телефон, аккаунт, точка, история; показ неподходящим и заблокированным; сверка с подписками §3; лента, поиск, SEO | 30 дней + 30 дней автору |
| Отклик | автор запроса; продавец — свой | `seen`, `accepted` продавцу | как запрос |
| Переписка после `accept` | как любая переписка | — | как переписка |

- «Моё» — на телефоне. На сервер — только значения стандартов, которые человек сам видит перед отправкой: текст «Ищу» —
  ровно то, что увидят продавцы; подписка §3 — как раньше.
- Продавец видит только числа. Контакт — только когда покупатель сам ответил (`accept`) и написал первым.
- **App Privacy:** «Ищу» — содержимое, которое человек показывает другим, связанное с аккаунтом: «Other User Content —
  Linked — App Functionality» (уже объявлено: чат, объявления) и «Search History — Linked» (§10.2, нужна в 83). Новых
  строк нет. Push «Сообщить им» — по подписке §3, цель та же (App Functionality). Числа `fit_demand` и
  `fit_notify.n` — из подписок для продавцов, как спрос §6: цель «Other Purposes» у «Search History» (§10.2, В3) нужна и
  им — до `fit_demand_post` и `fit_notify_on_publish`, если её ещё не добавили для `demand_stats`.
- **App Review:** все три ключа включаются после проверки сборки — описать в App Review Notes (§7.3, правило 2.3.1);
  «Сообщить им» не продаётся (3.1.1); «Ищу» и отклики — пользовательский контент с жалобой и блокировкой (1.2).

**Политика на kliko.kz** — дополнить §10.3 до `fit_demand_post`, `fit_notify_on_publish` и `wanted_std`:

> «Продавцам при подаче мы показываем только общее число подписок «Новинки для моего», которым подойдёт их вещь, —
> округлённо и не меньше 20. Если продавец нажмёт «Сообщить им», Kliko сам пришлёт уведомление подходящим подпискам в
> их обычном пределе — продавец не узнает, кому. Запрос «Ищу» видят только продавцы с подходящими объявлениями: текст,
> параметры, цену и город — без вашего имени и телефона; при подаче продавцы видят и число таких запросов. Имя увидит
> только продавец, которому вы сами ответите в чате. Запрос живёт 30 дней, удалить его можно в любой момент.»
