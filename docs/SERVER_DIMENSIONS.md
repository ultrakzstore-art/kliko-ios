# Габариты в объявлениях — что нужно от сервера

Документ для разработчика сайта kliko.kz (ultra-site). Просьба владельца (14.10.2026): «добавь линейку для габаритных
вещей и главное чтобы он работал; **габариты обязательно на будущее**».

Зачем: у мебели и крупной техники в приложении есть «Поместится ли?» — покупатель ставит в своей комнате AR-коробку
настоящих размеров вещи (`Sources/Native/TryOn/FitBox*.swift`). Сейчас размеры приходится выискивать в описании, и часто
их нет вовсе. С версии **1.12** приложение **требует** ширину, высоту и глубину при подаче и правке объявления в
габаритных разделах. Сервер нужен, чтобы эти три числа хранились отдельными полями, проверялись так же на сайте и
отдавались покупателю.

| Что | Где | Кто |
|---|---|---|
| Блок «Габариты, см» (Ш/В/Г) в подаче и правке, обязательный | приложение | **готово** |
| Поля `dim_w` · `dim_h` · `dim_d` в `submit` и `edit_item` | приложение шлёт уже сейчас | сервер: принять и хранить (раздел 4) |
| Строка «Габариты (Ш×В×Г): 60×85×55 см» в конце описания | приложение, **пока сервер не объявил поля** | сервер: ничего; после поддержки — по желанию убрать (4.4) |
| Признак `dims` в схеме формы | `api/app_post_schema.php` | сервер (раздел 3) |
| Отказ `need_dims` | `submit`, `edit_item` | сервер (4.2) |
| Отдача в `specs` и плоскими полями | `api/listings.php`, страница объявления, `my_items` | сервер (раздел 5) |
| Предложение размеров от Kliko AI | `recognize`, `accept_draft` | сервер, по желанию (раздел 6) |
| Тот же обязательный блок на сайте | форма кабинета | сервер (раздел 7) |
| Перенос размеров старых объявлений в поля | фоновая задача | сервер, по желанию (раздел 8) |

## 1. Соглашение о полях

Одно на всё (приложение, сайт, API, примерочная):

| Ключ | Значение | Подпись (ru) | kk | en | ar |
|---|---|---|---|---|---|
| `dim_w` | ширина, **целые сантиметры** | «Ширина, см» | «Ені, см» | «Width, cm» | «العرض، سم» |
| `dim_h` | высота, целые см | «Высота, см» | «Биіктігі, см» | «Height, cm» | «الارتفاع، سم» |
| `dim_d` | глубина, целые см | «Глубина, см» | «Тереңдігі, см» | «Depth, cm» | «العمق، سم» |

- Каждое — **целое от 1 до 1000**. Дробь, ноль, пусто, больше 1000 — не годится.
- Ширина — вдоль лицевой стороны, высота — от пола до самой высокой точки, глубина — от лица до задней стенки. Мерить
  по самым выступающим точкам: с ручками, ножками, подлокотниками.
- Ковёр: ширина и длина — в `dim_w` и `dim_d`, высота — толщина (обычно 1).
- Телевизор и монитор, которые продают с подставкой, — с подставкой.
- В базе хранить числами (не строкой «60 см»): по ним в будущем можно фильтровать витрину («шириной до 80 см»).

## 3. Схема формы: `GET /api/app_post_schema.php`

Приложение берёт форму подачи из схемы (`Sources/Native/Posting/PostingSchema.swift`). Для габаритов в ответ добавить:

```json
{
  "ok": true,
  "v": "2026-10-14-2",
  "dims": 1,
  "categories": [
    { "id": "sofas", "parent": "furniture", "root": "home-garden", "dims": true, "photo_max": 5, "extra": ["pay", "del", "trust"] },
    { "id": "tv", "parent": "tv-audio", "root": "electronics", "dims": true, "brand_req": true },
    { "id": "smartphones", "parent": "phones-tablets", "root": "electronics", "brand_req": true }
  ],
  "fields": {
    "sofas": [
      { "key": "dim_w", "type": "number", "label": "Ширина", "unit": "см", "required": true, "step": "1" },
      { "key": "dim_h", "type": "number", "label": "Высота", "unit": "см", "required": true, "step": "1" },
      { "key": "dim_d", "type": "number", "label": "Глубина", "unit": "см", "required": true, "step": "1" }
    ]
  }
}
```

- `dims: 1` **в корне** — «сервер принимает `dim_*` в `submit`/`edit_item`, хранит и отдаёт». С ним приложение
  **перестаёт** дописывать строку габаритов в описание. Ставить, только когда разделы 4 и 5 уже работают.
- `dims` **у раздела** — `true`: Ш×В×Г обязательны; `false`: не нужны. Нет ключа — решает список приложения. Признак
  наследуется так же, как остальные (сервер уже разрешил дерево — ставьте у каждого раздела, как `rentable`).
- Поля `dim_w` · `dim_h` · `dim_d` в `fields` раздела приложение тоже читает как «раздел габаритный» (если нет `dims`).
  Рисует оно всё равно свой блок (три поля, рисунок коробки, подсказка «где взять»), а не обычные поля схемы.
- «Сервер знает поля» приложение понимает **только** по `dims: 1` в корне. `dims` у разделов и поля `dim_*` в `fields`
  решают лишь, показывать ли блок: пока корня нет, строка «Габариты (Ш×В×Г): …» в описании остаётся (раздел 4.3).
- Сменить `v` — ETag схемы поменяется, приложения подхватят без новой сборки.

## 4. `submit` и `edit_item` (`cabinet.php?action=…`)

### 4.1. Что приходит

В теле — три новых целых (только в габаритных разделах и только когда все три заполнены):

```json
{ "category": "sofas", "title": "Диван угловой", "description": "…\n\nГабариты (Ш×В×Г): 220×90×160 см",
  "dim_w": 220, "dim_h": 90, "dim_d": 160, "…": "остальные поля как раньше" }
```

Сохранить у объявления: отдельными полями (`dim_w`, `dim_h`, `dim_d`) и в характеристиках (`specs`) — раздел 5. В
`edit_item` полей нет (раздел не габаритный, или старое приложение) — **прежние значения не трогать**.

### 4.2. Проверка и отказ `need_dims`

В габаритном разделе (по той же логике, что `dims` в схеме):

- нет хотя бы одного из трёх, не целое, вне 1…1000 → отказ;
- наибольшая сторона больше «наибольшего» из таблицы раздела 2 → отказ (текст — про миллиметры).

```json
{ "ok": false, "code": "need_dims", "error": "Укажите габариты: ширину, высоту и глубину в сантиметрах" }
```

- `error` — **готовый текст на языке запроса** (`lang`, как у остальных ответов кабинета). Пусто или машинный код
  (`need_dims`) — приложение покажет свой текст.
- Приложение ставит текст строкой под блоком «Габариты, см», переводит на шаг «Характеристики» и прокручивает к
  блоку; раздел, где сервер потребовал габариты, до перезапуска считает габаритным, даже если его нет в списке.
- Тот же `need_dims` — в `edit_item`. Приложение 1.12 и само не сохраняет правку габаритного объявления без размеров
  (рубильник `Config.габаритыОбязательныВПравке`), поэтому продавцы старых объявлений дозаполнят их при первой правке.
  Если хотите мягче для старых объявлений — не требуйте в `edit_item`, но **не стирайте** присланные значения.
- Старые приложения (до 1.12) полей не шлют. Чтобы не ломать им подачу, проверку можно включать по признаку нового
  клиента: в теле есть хоть один `dim_*` **или** версия приложения ≥ 1.12 (метка `KlikoApp/<версия>` в User-Agent
  страницы приложения). Форма сайта требует всегда (раздел 7).

### 4.3. Строка в описании — пока поля не объявлены

Пока в корне схемы нет `dims: 1`, приложение дописывает **последней строкой** описания:

```
Габариты (Ш×В×Г): 220×90×160 см
```

- Через пустую строку после текста продавца; описание вместе с ней — не длиннее 5000 знаков.
- При правке приложение вынимает эту строку из текста в блок и при сохранении ставит одну свежую — строк не
  накапливается.
- Её понимает разбор размеров «Поместится ли?» (`РазборГабаритов`, `FitBoxSize.swift`), поэтому AR работает уже сейчас,
  даже без поддержки на сервере.
- Образец для поиска (многострочный режим, без учёта регистра):
  `^\s*Габариты\s*\(Ш\s*[×xх*]\s*В\s*[×xх*]\s*Г\)\s*:\s*(\d{1,4})\s*[×xх*]\s*(\d{1,4})\s*[×xх*]\s*(\d{1,4})\s*см\.?\s*$`

### 4.4. После поддержки полей

Когда `dims: 1` появится в схеме, новые подачи придут без строки. Строку из описаний, пришедших **вместе** с `dim_*`, сервер
может убрать (по образцу выше) — размеры и так видны в характеристиках. Если строка есть, а полей нет (старый кэш
схемы) — заполнить `dim_*` из строки (это и есть миграция, раздел 8).

## 5. Отдача

### 5.1. Лента, карточка, страница объявления (`api/listings.php` и т. п.)

В `specs` объявления — три пункта с **ключом**:

```json
"specs": [
  { "key": "dim_w", "label": "Ширина, см", "value": "220" },
  { "key": "dim_h", "label": "Высота, см", "value": "90" },
  { "key": "dim_d", "label": "Глубина, см", "value": "160" }
],
"dim_w": 220, "dim_h": 90, "dim_d": 160
```

- `label` — на языке запроса (таблица раздела 1). Разбор приложения узнаёт русские, казахские и английские подписи, а
  арабские — только по `key`, поэтому **`key` обязателен**.
- Плоские `dim_w` · `dim_h` · `dim_d` (числа) — самый надёжный путь для «Поместится ли?»: без разбора подписей.
- Порядок в `specs` — Ш, В, Г подряд (на странице сайта можно показать одной строкой «Габариты: 220 × 90 × 160 см»).

### 5.2. `cabinet.php?action=my_items` (правка)

В записи объявления — плоские `dim_w`, `dim_h`, `dim_d` (числа или строки с числом). Приложение подставляет их в блок
правки. Нет полей — ищет в `specs`/`characteristics` (по `key` или русской подписи), потом — строку раздела 4.3 в
описании, потом — размеры в тексте описания (тогда с пометкой «нашли в объявлении — проверьте»).

## 6. Kliko AI: `recognize` и `accept_draft`

В `fields` ответа (`cabinet.php?action=recognize`, `api/ai_image.php?action=accept_draft`) можно отдавать:

```json
"fields": { "category": "fridges", "brand": "…", "title": "…", "dim_w": 60, "dim_h": 203, "dim_d": 68, "…": "…" }
```

- Только когда размеры **известны**, а не угаданы по фото: с наклейки или из инструкции на снимке, из паспорта модели,
  если модель распознана точно (до буквы артикула). Не уверены — не присылайте поля вовсе.
- Целые сантиметры, порядок — Ш, В, Г. Запасные виды, которые приложение тоже поймёт: `"dims": {"w": 60, "h": 203,
  "d": 68}` или `"dimensions": "60×203×68"`.
- Приложение ставит их **предложением** с пометкой «Размеры предложил Kliko AI — сверьте с инструкцией или рулеткой»;
  введённое продавцом не перезаписывает. Галочка «Проверил характеристики» черновика ИИ (договор ИИ-фото §9.4) их тоже
  покрывает.

## 7. Форма на сайте

В форме подачи и правки кабинета для габаритных разделов — тот же обязательный блок: «Габариты, см», три числовых поля
(Ширина · Высота · Глубина, `inputmode="numeric"`), подсказка «Где взять: в инструкции или на наклейке (сзади или внутри
двери). Нет — измерьте рулеткой по самым выступающим точкам, с ручками и ножками.», у ковров — «высота — толщина», у
ТВ — «с подставкой». Ошибка — тем же текстом, что `need_dims`.

## 8. Перенос старых объявлений (по желанию)

Фоновая задача по объявлениям габаритных разделов без `dim_*`:

1. Строка раздела 4.3 в описании — взять как есть.
2. Характеристики: «Ширина/Высота/Глубина» (и «Длина» — в ширину, прежняя ширина — в глубину) с единицами мм/см/м
   из значения или подписи; «Габариты/Размеры (Ш×В×Г), мм: 600×850×550» — порядок по буквам.
3. Описание: «габариты 60х85х55 см», «ширина 60 см, высота 85…» — только рядом со словами «габариты», «размер» или с
   единицами, и не про упаковку, нишу, спальное место, экран.
4. Перевести в сантиметры, округлить до целых; брать **только однозначное**: все три, единицы ясны, наибольшая сторона в
   рамках раздела 2. Иначе — не трогать: приложение попросит размеры при следующей правке.
5. Описание не менять. Пометить источник (`dims_src: "migrated"`), чтобы при желании показать «по описанию продавца».

Те же правила уже есть в приложении (`РазборГабаритов`, `Sources/Native/TryOn/FitBoxSize.swift`) — можно сверяться.

## 9. Проверка

- [ ] `app_post_schema.php`: `dims` у габаритных разделов и их потомков; `dims: 1` в корне — после пунктов ниже.
- [ ] `submit` с `dim_w/h/d` в разделе `sofas` → объявление с полями и тремя пунктами `specs` (с `key`).
- [ ] `submit` в `sofas` без полей (новый клиент) → `{"ok":false,"code":"need_dims","error":"…"}` на языке запроса.
- [ ] `submit` в `washing-machines` с `600×850×550` → `need_dims` с текстом про миллиметры.
- [ ] `edit_item` без `dim_*` в негабаритном разделе → прежние значения на месте.
- [ ] `my_items` и `api/listings.php` отдают плоские `dim_*` и `specs` с `key`.
- [ ] Описание со строкой «Габариты (Ш×В×Г): …» и `dim_*` после `dims: 1` — строка убрана (если решили убирать).
- [ ] Форма сайта требует габариты в тех же разделах.

## 10. Что в приложении (для справки)

- `Sources/Native/Posting/PostingDims.swift` — правила, разбор, отправка, рубильники `Config.габаритыВПодаче` (блок
  вообще) и `Config.габаритыОбязательныВПравке` (требовать ли в правке).
- `Sources/Native/Posting/PostingDimsView.swift` — блок «Габариты, см»; `PostingDimsText.swift` — тексты ru/kk/en/ar.
- `Sources/Native/Posting/PostingSchema.swift` — чтение `dims` из схемы.
- Подача (`PostingModel.swift`, `PostingSend.swift`): проверка в «Далее» шага «Характеристики», в «Опубликовать» и
  «Сохранить»; поля `dim_*` в `submit` и `edit_item`; отказ `need_dims`.
